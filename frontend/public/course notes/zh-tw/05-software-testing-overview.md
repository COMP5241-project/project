# 軟體測試總覽

> 整理自課程簡報(60 頁)。測試基礎(happy path / 邊界 / 負面)、靜態 vs 動態測試、DRE、測試金字塔、unit/integration/UI 測試(含 Playwright)、TDD,以及可用性測試。

---

## 1. 什麼是軟體測試

一項**調查**,目的是向持份者提供關於被測產品品質的資訊。品質面向:滿足使用者需求、符合需求、無錯誤與失效、適用性、客戶滿意度、付費意願。

### 三種基本測試風格(以 LLM 文件 App 為例)

- **Happy path(正常路徑)** — 使用者依預期流程、用有效輸入操作:上傳符合限制的支援格式 `.pdf`,App 成功解析並送給 LLM。
- **Edge case(邊界情況)** — 極端但有效、處於正常行為邊界的輸入:
  - 檔案大小恰好等於 Supabase 上限;檔名極長;文件打到 LLM 的上下文視窗上限;首次回應前快速連點「總結」;上傳中途離開頁面再回來。
  - 相關 API 錯誤:`200 OK`、`400 Bad Request`(內容過濾/請求無效)、`429 Too Many Requests`(速率限制)、`500 Internal Server Error`。
- **Negative testing(負面測試)** — 系統應拒絕或優雅處理的無效輸入與錯誤條件:不支援的檔案類型(`.exe`、`.mp4`、`.zip`)、損壞的 PDF、超大小限制、呼叫 LLM API 時的例外、短時間內重複提交總結請求。

## 2. 缺陷、測試類型、成本

- 多項研究顯示:**軟體缺陷的主要來源是規格與設計** — 不是編碼。
- **動態測試** — 以測試用例執行程式以偵測缺陷。
- **靜態測試** — 測試**未執行**的東西:審查程式碼與文件(需求規格、設計、使用者手冊、測試計畫、測試用例)以定位錯誤。(非軟體件也可能有 bug,應被測試。)
- **修 bug 的成本隨發現時機越晚越高** — 盡早發現缺陷。

### 可驗證(可測試)的需求

> 需求可驗證,當且僅當存在某種有限且成本有效的流程,讓人或機器能檢查產品是否滿足該需求。

- 不可驗證:「運作良好」、「使用者友善」、「通常會發生」。
- 可測試 NFR 範例:~~「醫務人員容易使用」~~ → 「醫務人員接受四小時訓練後應能使用系統所有功能;訓練後,經驗使用者的平均錯誤率不得超過每小時兩次。」

### 缺陷移除效率(DRE, Defect Removal Efficiency)

- 好的測試流程應**增加測試者發現的缺陷數、減少客戶發現的缺陷數**,並盡早偵測。
- **DRE = (偵測並移除的缺陷數) / (缺陷總數)**,其中總數 = 開發期間發現的 + **發布後第一年**回報的。
- 例:開發期間找到 1000 個 + 第一年回報 100 個 → 總計 1100。
- **練習**:A 團隊測試中找 30 / 使用者找 70(DRE ≈ 30%);B 團隊找 20 / 30(DRE ≈ 40%)→ **B 更有效**,儘管總數較少。
- 每個階段都可能注入*與*移除缺陷;測試主要負責移除 — 且修錯缺陷本身可能引入新缺陷。

## 3. 手動 vs 自動化測試

### 手動測試

人類不使用自動化工具、手工執行測試用例(例:購物車範例 — 加 2× $19.99 + 1× $9.99 → 驗證「3 items」與「$49.97」)。

| 優勢 | 劣勢 |
|---|---|
| 可用性測試(介面是否直覺) | 耗時 |
| 視覺驗證(版面、色彩、響應式) | 易出錯(人類計算失誤) |
| 探索式測試(意外 bug) | 不可重現(不同測試者執行不同) |
| 整體 UX 感受與流暢度 | |

### 自動化測試

用軟體控制測試執行。Agile 短週期使手動回歸測試幾乎不可能。**層級**(快/便宜 → 慢/貴):**單元測試 → service 層測試 → UI 測試**。

撰寫自動化測試的方式:**手寫腳本**、**錄製式**(工具捕捉 UI 互動供重放)、**GenAI 輔助**(如 GitHub Copilot)。

## 4. 單元測試

- 以程式碼驗證小型、隔離的單元(單一函式/方法)是否如預期。框架:**pytest**(Python)、**JUnit**(Java)、**Jest/Mocha**(JS)。
- **斷言(assertion)** = 檢查某條件為真的陳述;為假 → 測試失敗。
- 範例(購物車:2× $19.99 + 1× $9.99):

```java
// JUnit — Arrange / Act / Assert
ShoppingCart cart = new ShoppingCart();
cart.addItem(2, 19.99);
cart.addItem(1, 9.99);
assertEquals(3, cart.getItemsCount(), "Cart should have 3 items after adding.");
assertEquals(49.97, cart.getTotalAmount(), 0.001, "Total amount should be 49.97");
```

```python
# pytest — 同一個測試
cart = ShoppingCart()
cart.add_item(2, 19.99)
cart.add_item(1, 9.99)
assert cart.get_items_count() == 3, "Cart should have 3 items after adding."
assert abs(cart.get_total_amount() - 49.97) < 0.001, "Total amount should be 49.97"
```

- **AAA 模式**:**Arrange**(準備物件、相依、輸入)→ **Act**(執行被測單元)→ **Assert**(驗證實際 vs 預期)。
- **相依與 flaky test**:等 IO/外部服務會殺死測試速度;依賴 live service/DB/网络的測試會間歇性失敗 → **flaky test** = 程式碼與環境未變但結果不一致。
- **Mock** — 模擬真實相依行為的擬製物件:控制回傳值、模擬錯誤,而不碰真實外部系統。

## 5. 整合測試

- 驗證多個元件協同運作:REST API endpoints、商業邏輯、資料庫。
- HTTP 是網頁的請求/回應協定;REST API 透過 HTTP methods(GET、POST、PUT、DELETE)交換資料。
- **Mocking**:API 跑真實商業邏輯、寫 app 自己的資料庫,但**外部服務(如付款業者)被 mock**,因為 app 不控制它們。

## 6. UI / 端到端測試(Playwright)

- **UI 測試**產生 UI 事件(按鍵、滑鼠)並觀察結果;**E2E** 在真實瀏覽器中測完整使用者流程。
- **Playwright**(Microsoft,開源):驅動真實瀏覽器(Chromium、Firefox、WebKit)。
  - **Semantic locator(語義定位)** — 依使用者認知找元素(「標示為『Card Number』的欄位」、「寫著 'Pay' 的按鈕）。
  - **Auto-waiting(自動等待)** — `expect` 斷言會重試到逾時。
  - **Happy path**:填付款表單 → API 驗證/向 Stripe 收費 → 斷言成功訊息 + Order ID(證明後端已處理)。
  - **Unhappy path**:空表單 → 必填欄位錯誤;用「declined」卡號 → UI 優雅處理 API 錯誤不崩潰。
  - **Mobile 版面**:程式化調整視窗尺寸;檢查表單響應式、按鈕不被裁切。
  - **Headed**(看著測試除錯)vs **Headless**(無視窗;適合快速 CI/CD)。
- **Playwright + MCP**(Model Context Protocol):讓 LLM 應用串接外部工具/服務的開放協定 — 讓 AI 代理以自然語言控制瀏覽器,不必每步寫新 script。
- **練習**:`git clone https://github.com/HKPolyUSE/playwright_testing`;在 IDE 設定 `@playwright/mcp` MCP server;跑登入 helper 範例(`doLogin` 用 `getByRole` locator)。

### UI 測試取捨

| 優勢 | 限制 |
|---|---|
| 永遠可自動化 | 比單元測試慢數個數量級 |
| 端到端覆蓋(UI → services → DB) | 脆弱:標籤從 "Submit" 改成 "Confirm" 就會打破 hard-code 選擇器 |
| 適合高階 **smoke test**(系統是否啟動、部署、連線) | E2E 失敗告訴你*有*問題,很少告訴你*在哪* |

### 自動化測試的整體好處

**快**(負載測試、大量隨機測試)、**可靠**(每次操作完全相同,消除人類失誤)、**可重現**(回歸測試)。

## 7. 測試形狀:金字塔 vs 甜筒

- **Ice cream cone(甜筒,反模式)**:大量手動測試 + 自動化集中在 UI 層;自動化只是在模擬慢速手動流程。
- **測試金字塔(Test pyramid)**:
  - **單元測試**(底) — 隔離的函式/方法;便宜、毫秒級、即時回饋。
  - **整合測試**(中) — 元件/services 協同:API endpoints、DB 操作、service 通訊。
  - **UI/E2E 測試**(頂) — 透過 UI 的完整使用者旅程。

## 8. 測試驅動開發(TDD)

- 常規流程:開發 → 寫測試 → 跑測試。
- **TDD 循環**:寫一個**失敗**的測試 → 執行(失敗)→ 寫剛好讓它通過的最少程式碼 → 執行 → **重構** → 重複(Red–Green–Refactor)。
- **「測試先行」是關於設計**:逼你先想清楚需求、設計 API/介面、決定程式碼如何使用。寫得好的單元測試是**運作中的規格**,也是技術文件的重要部分。
- **剛好夠用的程式碼**:失敗的測試標出了差距;只寫讓它通過的(實作可能非最佳 — 之後重構)。
- **重構**:在不改變外部行為的前提下改善設計。
- **TDD 優勢**:測試成為正確行為的合約;自動化測試每次 check-in 都跑;團隊交付功能時不怕意外改動系統。附加價值:**約束 AI** — 測試限制 AI 的修改必須通過所有既有測試,防止它改壞正確的功能。

## 9. 可用性測試

- 測試使用者使用介面的容易程度(在真實使用者身上測試)。**五個構面**(Nielsen):**Learnability(易學性)、Efficiency(效率)、Memorability(記憶性)、Errors(錯誤:數量/嚴重度/恢復)、Satisfaction(滿意度)**。
- **改善可用性**:邀約代表使用者做真實任務;**觀察**他們在哪停滯、犯錯、困惑(不只靠印象);先修最大的問題;再測;在全部五構面上迭代。
- **Guerrilla testing** — 低成本、「野外」測試。
- **執行流程**:系統準備好停在起始頁;facilitator 派發任務;詢問思考過程;記錄建議;讓開發者/設計者觀察;結束訪談(喜/厭、建議);產出**最終報告**(有效性、效率、任務時間、錯誤、滿意度)。
- **受測者**:識別並招募(排程、地點、facilitator、記錄員);**獎勵**(免費午餐、禮品券)能提升出席率。
- **Usability lab**:簡單單間 → 電子觀察室。
- **Think-aloud(唸出想法)**:受測者邊做邊口述思考;聆聽他們在做什麼、找什麼、覺得難在哪;溫和提示(「你現在在想什麼?」)。
- **測試設計**:
  - **Between-subjects(獨立群組)** — 每個部分由獨特使用者測試;緩解**學習轉移**(用過 A 會讓 B 變簡單),避免掩蓋後期問題。
  - **Within-subjects** — 每個受測者測全部模組;用**counterbalancing**(隨機/平衡任務順序)+ 場次間休息。
- **收集數據**:
  - *效能*:任務完成時間、正確完成率(有/無提示)、錯誤數、錯誤恢復時間、查手冊次數、負面評論數。
  - *評分 + 理由*:有用性、符合預期、易用/易學/易設定/易無障礙、幫助品質。
  - *偏好 + 理由*:本原型 vs 另一原型、vs 競品、vs 舊概念模型。

## 10. 重點 takeaway

- 測使用者做的(happy path)、邊界的(edge)、失敗的(negative)— 三者都要。
- 多數缺陷源自規格/設計 → 早期靜態測試(審查)是最便宜的缺陷移除。
- 需求必須可驗證;用 DRE 度量你的流程。
- 自動化按金字塔形狀:大量快速單元測試、較少整合測試、最少 E2E。
- mock 外部相依以保持測試快而穩;避免 flaky test。
- TDD 把測試變成活規格 — 也是 AI 生成變更的護欄。
- 可用性要靠量測,不靠假設:觀察真實使用者、think-aloud、產出有證據的報告。
