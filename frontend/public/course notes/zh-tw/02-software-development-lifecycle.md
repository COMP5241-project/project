# 軟體開發生命週期(SDLC)

> 整理自課程簡報(57 頁)。涵蓋需求、設計、實作、測試、部署與維護——包含 Verification(確認)與 Validation(驗證)的區別、部署策略,以及一個部署失敗案例研究。

---

## 1. 什麼是 SDLC

一個描述軟體開發各階段的結構化流程。1970 年代為管理大型企業系統而發展,至今仍適用。

階段:**需求分析 → 系統設計 → 實作 → 單元測試 → 整合測試 → 系統測試 → 驗收測試 → 部署 → 維護**。

## 2. 需求

### 功能性 vs 非功能性

- **功能性需求**定義系統*要完成什麼*(例:「建立帳號時寄送確認信」、「依搜尋字串搜尋項目」、「結帳前檢視/修改/移除購物車項目」、「社群帳號登入」、「通知推送」、「回饋/評分」)。
- **非功能性需求**定義系統*運作得如何*(效能、安全、可用性等)。

### 收集功能性需求

| 方法 | 目的 |
|---|---|
| 文件分析 | 檢視既有商業流程/系統,識別需求 |
| 觀察 | 在真實環境中觀察使用者(工作流、痛點) |
| 訪談 | 與持份者一對一深入討論需求與預期 |
| 問卷調查 | 向大樣本收集量化資料 |
| 焦點小組 | 收集多元持份者觀點 |
| 原型 | 建立早期版本,視覺化需求並收集回饋 |

AI 可以輔助(例如把 Zoom 會議摘要成需求)——但**務必檢查 AI 輸出是否正確、修飾後再與客戶確認**。

### 需求擷取與管理

- **擷取(Elicitation)**:識別持份者 → 收集資訊(訪談、問卷、工作坊)→ 文件化。
- **管理**:優先級排序(哪些需求最必備、先做);變更管理(受控處理變更,防止範圍蔓延);驗證與確認(系統滿足所有已識別的狀態,且這些需求符合其預定目的)。

### 挑戰與解法

挑戰:持份者無法清楚表達需求;不同持份者優先級與假設互相衝突;商業需求隨時間變動、持份者反復。

- **問更好的問題**:從問題出發而非解法(「我們解決什麼痛點?商業價值是什麼?」);開放式、流程導向的問題(「你現在怎麼做?哪裡會卡住?你做決策需要什麼資訊?」);挑戰假設(「如果資料缺失呢?例外情況是什麼?誰拍板?」);用 **5 Whys** 找到根因而非症狀。
- **綜合、釐清並解決衝突**:會中複述確認(「我聽到的是……對嗎?」);把模糊說法轉成可測試、具體的需求或業務規則;用 **MoSCoW**(Must/Should/Could/Won't)幫助持份者達成「現在必備 vs 之後再做」的共識。

## 3. 原型與 MVP

- **線框圖(Wireframe)**——網站/App 的低保真圖形結構,映射頁面區塊與互動元素。**模型圖(Mockup)**——靜態但更真實地呈現最終產品(品牌、色彩、字體、圖示)。**高保真原型**——最接近最終產品;同時測試視覺與使用者流程的反應。
- **類型**:丟棄式(快速建立以收集回饋、修飾需求,用完即棄)/ 演化式(根據回饋增量精煉至最終版)/ 增量式(把最終產品切成零件,各部分獨立開發、最後整合)。
- 「我說不出我要什麼,但看到了我才知道。」

### MVP(最小可行產品)

- 當建構獨特且不确定的產品時,市場驗證至關重要:以最少努力,收集**最多經驗證的客戶學習**。Minimum = 盡可能少花時間與精力;Viable = 品質足以準確評估客戶會不會使用。
- 用真實使用者測試點子 → 收集關鍵價值指標 → 做出下一個 MVP,循環進行;降低做出不具經濟可行性產品的風險。

| 面向 | 原型 | MVP |
|---|---|---|
| 目的 | 測試與視覺化概念、設計、UX | 向使用者交付核心功能 |
| 功能性 | 常無功能或功能有限 | 核心功能完整可用 |
| 市場準備 | 不適合上市 | 可上市 |
| 回饋重點 | 對設計與可行性的初期回饋 | 對產品價值與易用性的真實使用者回饋 |
| 開發階段 | 早期、完整開發前 | 早期上線、第一個可用版本 |
| 目標 | 驗證設計想法與技術可行性 | 驗證商業點子、吸引使用者 |

## 4. 設計與實作

- 需求規格說明**是什麼(what)**;設計說明**如何做到(how)**。
- **系統設計面試**:技術評估,要求候選人在白板/虛擬畫布上設計可擴展的軟體系統——展示其對需求、取捨、元件互動的推理能力。
- **範例:GenAI 聊天 App**——Python Flask API 後端(商業邏輯、資料存取;接收前端問題、轉給 AI 服務、回傳答案)+ React 前端(輸入問題、檢視答案的 UI;以 API 請求送出問題、顯示回應)+ OpenAI Azure 服務(GenAI API 以語言模型回答)+ 資料庫(儲存過去對話)。
- **API key 保護:**
  - 開發期:密鑰放 `.env`(本地環境變數);`.gitignore` 把 `.env` 與敏感檔案排除在版本控制外。**密鑰絕不能出現在遠端 repository。**
  - 生產期:密鑰安全儲存在線上平台(例:Vercel 環境變數設定),部署時注入執行中的應用,對公開與前端程式碼不可見。

## 5. 測試階段

- **單元測試**:個別單位(程序、函式、方法、類別)按單元設計規格**隔離測試**;缺陷容易定位。
- **整合測試**:模組組合後群組測試——即使模組本身正確無 bug,兩個以上模組整合時仍可能出錯(例:呼叫端誤解被呼叫端的介面規格)。
- **系統測試**:驗證系統實現了需求規格中的所有需求——功能性(實現全部功能)、健壯性(從錯誤狀態恢復)、互操作性(與第三方系統互動)、效能(吞吐量、回應時間)、擴展性(規模增大時的行為,例:使用者數)、可靠性(長期穩定運作)、文件測試(使用者指南準確可用)。
- **Pull Request(PR)**:開發者提議把一個 branch 的變更合併進另一個 branch,讓團隊在整合前討論、審查、核准。
- **確認測試(Confirmation)**:重跑上次失敗的測試用例,驗證修正有效。
- **回歸測試(Regression)**:修改後對先前已測過的程式重測,確保未對未改動區域引入缺陷。可重跑所有測試用例(自動化可加速),或挑選達到/與被修改陳述/模組相關的一組。
- **測試自動化**:用軟體控制測試執行;單元測試是檢查某段程式碼(方法)是否如預期運作的程式碼(例:Java 的 JUnit)。
- **微軟的自動化測試**:「我們每個 pull request 跑 6 萬多條單元測試」「在 7 分鐘內跑完六萬條左右」。
- **驗收測試**:客戶/終端使用者依驗收標準(功能、效能、安全等)驗證系統是否「做對了」。
  - **Alpha 測試**:在開發者場地,使用者在開發者駐場下進行。
  - **Beta 測試**:在多個使用者場地,無開發者參與——更接近系統真實使用。

### Verification(確認)vs Validation(驗證)

- **Verification(確認)**——評估是否走在正確軌道上、最終產品被**正確地**建構。例:code review、單元/整合/系統測試;通常由開發者執行,確保符合需求且實作正確。
- **Validation(驗證)**——評估軟體是否符合使用者/業務需求,確保建構了**正確的**產品。例:原型、驗收測試、可用性測試、生產環境測試、A/B 測試。
- Validation 會帶來改進軟體的**新需求**(feedback loop)。

## 6. 部署與環境

- 軟體部署到客戶環境,或發布到市場/生產。
- **Dev vs Production 差異**:不同 OS 版本與函式庫;生產資料可能含 dev 沒有的邊界情況與量級;生產環境可能有更嚴格的存取控制/防火牆;不同的資源上限;依賴的對外服務行為可能不同。「在我機器上能跑」≠「對真實使用者能跑」。

## 7. 維護

- 部署到生產**之後**對軟體產品的修改:修生產環境的 bug 與問題、發布修補、提升產品與效能、發布含增強的新版本。
- **60/60 法則**(IEEE Software, 2001):維護平均佔**軟體生命週期成本的 60%**;維護的約 60% 是在保持系統運作、不破壞的前提下新增功能。在 clean-slate(從零設計)專案中,維護常比開發更具挑戰。
- **ISO/IEC 14764:2006** 維護類型:**Corrective(糾正)**修缺陷;**Adaptive(適應)**隨環境變化保持相容;**Perfective(完善)**提升效能或可維護性;**Preventive(預防)**提前處理潛在問題。

### 部署失敗案例研究

- 凌晨 1:00:新功能部署完成,即時健康檢查全過,系統看似穩定。
- 凌晨 3:00:新查詢開始級聯,回應時間顯著惡化——事故開始,**卻沒有警報**。
- 上午 10:00:才發現事故——7 小時應用實質不可用,營運團隊卻不知情。
- 調查:應用與資料庫日誌顯示伺服器資源耗盡與高延遲;與凌晨 1:00 的部署相關 → **根因**:新功能引入缺少適當索引的低效查詢,鎖住資源導致全域減慢。
- 緩解:重寫問題查詢、補上索引;patch v1.1 先在 staging 環境驗證(回應時間改善、無錯誤),再部署上生產;即時監控指標確認 DB 負載下降。**晚 9:00 服務恢復**,事故在效能退化開始 18 小時後正式關閉。

| 指標 | 定義 | 本案 |
|---|---|---|
| **TTD**(發現時間) | 失敗開始 → 團隊知覺 | 7 小時(凌晨 3 點 → 上午 10 點) |
| **TTM**(緩解時間) | 團隊的運維速度:診斷、修復、驗證 | 約 8 小時(查詢優化的複雜度主導) |
| **TTR**(恢復時間) | 對客戶的總影響時長 | 18 小時(凌晨 3 點 → 晚 9 點) |

## 8. 可用性

- **可用性 = Uptime / (Uptime + Downtime)** = MTTF / (MTTF + MTTR),以「9」的個數描述:

| Uptime | 每週停機 | 每月停機 | 每年停機 |
|---|---|---|---|
| 99% | 1.68 小時 | 7.2 小時 | 3.65 天 |
| 99.9% | 10 分鐘 | 43.2 分鐘 | 8.76 小時 |
| 99.95% | 5 分鐘 | 21.6 分鐘 | 4.38 小時 |
| 99.99% | 1 分鐘 | 4.32 分鐘 | 52.56 分鐘 |
| 99.999% | 6 秒 | 26 秒 | 5.26 分鐘 |

- 影響可用性的因素:硬體故障、網路不穩、軟體 bug、維護停機、資安攻擊(DDoS、惡意程式)、斷電、容量過載、設定錯誤、第三方中斷、備份/恢復不良。

## 9. 部署策略

| 策略 | 運作方式 | 取捨 |
|---|---|---|
| **Big Bang** | 一次性上線新版本,伴隨服務停機;失敗則回滾到上一版 | 對公眾/業務關鍵應用風險高;需要發布前充分開發測試;停機且難以回滾 |
| **Rolling upgrade(滾動升級)** | 新版本逐步替換舊版;新舊版本共存一段時間 | 不相容的新元件可回滾 |
| **Blue-Green(藍綠部署)** | 兩套相同生產環境並行;Blue 接收全部流量;Green 部署新版本並測試功能與效能;通過後把流量從 Blue 切到 Green | Green 上線出問題,流量切回 Blue 即回滾 |
| **Canary(灰度/金絲雀)** | 只升級一小部分執行個體;把部分使用者導向 canary 執行個體;無誤再逐步擴大 | 降低新版本上生產的風險 |
| **Feature flag(功能旗標)** | **不部署新程式碼**即可控制特定功能的可見性與啟用 | 發布與上線解耦 |

### Big Tech 如何把程式碼上到生產

1. 開發期持續用 Git commit,追蹤每個變更。
2. commit 後由 **CI/CD** 伺服器(例:CircleCI)接管:自動 build、跑單元測試、品質檢查。
3. 上線前進入獨立 **QA 環境**,QA 團隊做回歸與效能檢查。
4. 生產發布使用特定策略與工具:feature toggle、canary 部署、A/B 測試。
5. **監控與可靠性**:上線後 SRE 用 Prometheus、Datadog 等監控工具盯系統效能,即時處理問題。

## 10. 重點 takeaway

- 需求品質決定下游一切;善用擷取技巧、MoSCoW、5 Whys。
- 原型驗證設計;MVP 驗證商業點子。
- Verification = 把產品做對;Validation = 做對的產品。
- 越早發現 bug 成本越低;分層測試(單元 → 整合 → 系統 → 驗收)。
- 部署是風險管理練習:按關鍵度與回滾需求選策略。
- 維護佔生命週期成本的大頭(60/60)——設計時就要考慮。
- 生產環境就是另一個環境:預期不同的資料、限制、依賴。
