# 软件开发生命周期(SDLC)

> 整理自课程讲义(57 页)。涵盖需求、设计、实现、测试、部署与维护——包括 Verification(验证/确认)与 Validation(确认/验收)的区别、部署策略,以及一个部署失败案例研究。

---

## 1. 什么是 SDLC

一个描述软件开发各阶段的结构化流程。1970 年代为管理大型商业系统而发展,至今仍适用。

阶段:**需求分析 → 系统设计 → 实现 → 单元测试 → 集成测试 → 系统测试 → 验收测试 → 部署 → 维护**。

## 2. 需求

### 功能需求 vs 非功能需求

- **功能需求**定义系统*要做什么*(例:"创建账号时发送确认邮件""按搜索词检索条目""结账前查看/修改/移除购物车条目""社交账号登录""推送通知""反馈/评分")。
- **非功能需求**定义系统*运行得如何*(性能、安全、可用性等)。

### 收集功能需求

| 方法 | 目的 |
|---|---|
| 文档分析 | 审阅现有业务流程/系统,识别需求 |
| 观察 | 在真实环境中观察用户(工作流、痛点) |
| 访谈 | 与干系人一对一深入讨论需求与期望 |
| 问卷 | 面向大样本收集量化数据 |
| 焦点小组 | 收集多元干系人视角 |
| 原型 | 创建早期版本,可视化需求并收集反馈 |

AI 可以辅助(例如把 Zoom 会议摘要成需求)——但**务必检查 AI 输出是否正确、润色后再与客户确认**。

### 需求提取与管理

- **提取(Elicitation)**:识别干系人 → 收集信息(访谈、问卷、工作坊)→ 文档化。
- **管理**:优先级排序(哪些需求最必要、先做);变更管理(受控处理变更,防止范围蔓延);验证与确认(系统满足所有已识别的需求,且这些需求符合其预定目的)。

### 挑战与解法

挑战:干系人无法清晰表达需求;不同干系人优先级与假设互相冲突;业务需求随时间变化、干系人反复。

- **问更好的问题**:从问题出发而非方案("我们在解决什么痛点?业务价值是什么?");开放式、流程导向的问题("你现在怎么做?哪里会卡?你决策需要什么信息?");挑战假设("如果数据缺失呢?例外情况是什么?谁拍板?");用 **5 Whys** 找到根因而非表象。
- **综合、澄清并解决冲突**:会中复述确认("我听到的是……对吗?");把模糊说法转成可测试、具体的需求或业务规则;用 **MoSCoW**(Must/Should/Could/Won't)帮助干系人达成"现在必备 vs 之后再做"的共识。

## 3. 原型与 MVP

- **线框图(Wireframe)**——网站/App 的低保真图形结构,映射页面区块与交互元素。**模型图(Mockup)**——静态但更真实地呈现最终产品(品牌、颜色、字体、图标)。**高保真原型**——最接近最终产品;同时测试视觉与用户流程的反应。
- **类型**:抛弃式(快速建立以收集反馈、细化需求,用完即弃)/ 演化式(基于反馈增量精化至最终版)/ 增量式(把最终产品切成部件,各部分独立开发、最后集成)。
- "我说不出我要什么,但看到了我才知道。"

### MVP(最小可行产品)

- 当构建独特且不确定的产品时,市场验证至关重要:以最少努力,收集**最多经验证的用户学习**。Minimum = 尽可能少花时间与精力;Viable = 质量足以准确评估用户是否会使用。
- 用真实用户测试想法 → 收集关键价值指标 → 做出下一个 MVP,循环进行;降低做出不具经济可行性产品的风险。

| 维度 | 原型 | MVP |
|---|---|---|
| 目的 | 测试与可视化概念、设计、UX | 向用户交付核心功能 |
| 功能性 | 常无功能或功能有限 | 核心功能完整可用 |
| 市场就绪 | 不适合上市 | 可上市 |
| 反馈重点 | 对设计与可行性的初期反馈 | 对产品价值与易用性的真实用户反馈 |
| 开发阶段 | 早期、完整开发前 | 早期上线、第一个可用版本 |
| 目标 | 验证设计想法与技术可行性 | 验证商业想法、吸引用户 |

## 4. 设计与实现

- 需求规格说明**是什么(what)**;设计说明**如何做到(how)**。
- **系统设计面试**:技术评估,要求候选人在白板/虚拟画布上设计可扩展的软件系统——展示其对需求、取舍、组件交互的推理能力。
- **示例:GenAI 聊天 App**——Python Flask API 后端(业务逻辑、数据存取;接收前端问题、转给 AI 服务、返回答案)+ React 前端(提问与查看答案的 UI;以 API 请求发送问题、显示响应)+ OpenAI Azure 服务(GenAI API 用语言模型回答)+ 数据库(存储历史对话)。
- **API key 保护:**
  - 开发期:密钥放 `.env`(本地环境变量);`.gitignore` 把 `.env` 与敏感文件排除在版本控制外。**密钥绝不能出现在远程仓库。**
  - 生产期:密钥安全存储在线平台(例:Vercel 环境变量设置),部署时注入运行中的应用,对公开与前端代码不可见。

## 5. 测试阶段

- **单元测试**:单个单元(过程、函数、方法、类)按其设计规格**隔离测试**;缺陷容易定位。
- **集成测试**:模块组合后成组测试——即使模块本身正确无 bug,两个以上模块集成时仍可能出错(例:调用方误解被调用方的接口规格)。
- **系统测试**:验证系统实现了需求规格中的所有需求——功能性(实现全部功能)、健壮性(从错误状态恢复)、互操作性(与第三方系统交互)、性能(吞吐量、响应时间)、可扩展性(规模增大时的行为,如用户数)、可靠性(长期稳定运行)、文档测试(用户指南准确可用)。
- **Pull Request(PR)**:开发者提议把一个分支的变更合并进另一个分支,让团队在集成前讨论、审查、批准。
- **确认测试(Confirmation)**:重跑上次失败的测试用例,验证修复有效。
- **回归测试(Regression)**:修改后对先前已测过的程序重测,确保未对未改动区域引入缺陷。可重跑全部测试用例(自动化可加速),或挑选达到/与被修改语句/模块相关的一组。
- **测试自动化**:用软件控制测试执行;单元测试是检查某段代码(方法)是否按预期工作的代码(例:Java 的 JUnit)。
- **微软的自动化测试**:"我们每个 pull request 跑 6 万多条单元测试""在 7 分钟内跑完六万条左右"。
- **验收测试**:客户/最终用户按验收标准(功能、性能、安全等)验证系统是否"做对了"。
  - **Alpha 测试**:在开发者场地,用户有开发者驻场下进行。
  - **Beta 测试**:在多个用户场地,无开发者参与——更接近系统真实使用。

### Verification vs Validation

- **Verification(验证)**——评估是否走在正确轨道上、最终产品被**正确地**构建。例:代码评审、单元/集成/系统测试;通常由开发者执行,确保符合需求且实现正确。
- **Validation(确认)**——评估软件是否满足用户/业务需求,确保构建的是**正确的**产品。例:原型、验收测试、可用性测试、生产环境测试、A/B 测试。
- Validation 会带来改进软件的**新需求**(反馈回路)。

## 6. 部署与环境

- 软件部署到客户环境,或发布到市场/生产。
- **Dev vs Production 差异**:不同 OS 版本与库;生产数据可能含开发环境没有的边界情况与量级;生产环境可能有更严格的访问控制/防火墙;不同的资源上限;依赖的外部服务行为可能不同。"在我机器上能跑"≠"对真实用户能跑"。

## 7. 维护

- 部署到生产**之后**对软件产品的修改:修生产环境的 bug 与问题、发布补丁、提升产品与性能、发布含增强的新版本。
- **60/60 法则**(IEEE Software, 2001):维护平均占**软件生命周期成本的 60%**;维护的约 60% 是在保持系统运行、不破坏的前提下增加新功能。在 clean-slate(从零设计)项目中,维护常比开发更具挑战。
- **ISO/IEC 14764:2006** 维护类型:**Corrective(纠正)**修缺陷;**Adaptive(适应)**随环境变化保持兼容;**Perfective(完善)**提升性能或可维护性;**Preventive(预防)**提前处理潜在问题。

### 部署失败案例研究

- 凌晨 1:00:新功能部署完成,即时健康检查全过,系统看似稳定。
- 凌晨 3:00:新查询开始级联,响应时间显著恶化——事故开始,**却没有告警**。
- 上午 10:00:才发现事故——7 小时应用实际不可用,运维团队却不知情。
- 调查:应用与数据库日志显示应用服务器资源耗尽与高延迟;与凌晨 1:00 的部署相关 → **根因**:新功能引入了缺少适当索引的低效查询,锁定资源导致全局变慢。
- 缓解:重写问题查询、补上索引;patch v1.1 先在 staging 环境验证(响应时间改善、无错误),再部署上生产;实时盯指标确认数据库负载下降。**晚 9:00 服务恢复**,事故在性能退化开始 18 小时后正式关闭。

| 指标 | 定义 | 本案 |
|---|---|---|
| **TTD**(发现时间) | 故障开始 → 团队察觉 | 7 小时(凌晨 3 点 → 上午 10 点) |
| **TTM**(缓解时间) | 团队的运维速度:诊断、修复、验证 | 约 8 小时(查询优化的复杂度主导) |
| **TTR**(恢复时间) | 对客户的总影响时长 | 18 小时(凌晨 3 点 → 晚 9 点) |

## 8. 可用性

- **可用性 = Uptime / (Uptime + Downtime)** = MTTF / (MTTF + MTTR),以"9"的个数描述:

| Uptime | 每周停机 | 每月停机 | 每年停机 |
|---|---|---|---|
| 99% | 1.68 小时 | 7.2 小时 | 3.65 天 |
| 99.9% | 10 分钟 | 43.2 分钟 | 8.76 小时 |
| 99.95% | 5 分钟 | 21.6 分钟 | 4.38 小时 |
| 99.99% | 1 分钟 | 4.32 分钟 | 52.56 分钟 |
| 99.999% | 6 秒 | 26 秒 | 5.26 分钟 |

- 影响可用性的因素:硬件故障、网络不稳、软件 bug、维护停机、安全攻击(DDoS、恶意软件)、断电、容量过载、配置错误、第三方中断、备份/恢复不良。

## 9. 部署策略

| 策略 | 运作方式 | 取舍 |
|---|---|---|
| **Big Bang** | 一次性上线新版本,伴随服务停机;失败则回滚到上一版 | 对面向公众/业务关键应用风险高;要求发布前充分开发与测试;停机且难以回滚 |
| **Rolling upgrade(滚动升级)** | 新版本逐步替换旧版;新旧版本共存一段时间 | 不兼容的新组件可回滚 |
| **Blue-Green(蓝绿部署)** | 两套相同生产环境并行;Blue 接收全部流量;Green 部署新版本并测试功能与性能;通过后把流量从 Blue 切到 Green | Green 上线出问题,流量切回 Blue 即回滚 |
| **Canary(金丝雀)** | 只升级一小部分实例;把部分用户路由到 canary 实例;无误再逐步扩大 | 降低新版本上生产的风险 |
| **Feature flag(功能开关)** | **不部署新代码**即可控制特定功能的可见性与启用 | 发布与上线解耦 |

### 大厂如何把代码上到生产

1. 开发期持续用 Git commit,跟踪每个变更。
2. commit 后由 **CI/CD** 服务器(例:CircleCI)接管:自动 build、跑单元测试、质量检查。
3. 上线前进入独立 **QA 环境**,QA 团队做回归与性能检查。
4. 生产发布使用特定策略与工具:feature toggle、canary 部署、A/B 测试。
5. **监控与可靠性**:上线后 SRE 用 Prometheus、Datadog 等监控工具盯系统性能,立即处理问题。

## 10. 重点 takeaway

- 需求质量决定下游一切;善用提取技巧、MoSCoW、5 Whys。
- 原型验证设计;MVP 验证商业想法。
- Verification = 把产品做对;Validation = 做对的产品。
- 越早发现 bug 成本越低;分层测试(单元 → 集成 → 系统 → 验收)。
- 部署是风险管理练习:按关键度与回滚需求选策略。
- 维护占生命周期成本大头(60/60)——设计时就要考虑。
- 生产环境就是另一个环境:预期不同的数据、限制、依赖。
