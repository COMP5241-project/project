# 软件测试概览

> 整理自课程讲义(60 页)。测试基础(happy path / 边界 / 负面)、静态 vs 动态测试、DRE、测试金字塔、unit/integration/UI 测试(含 Playwright)、TDD,以及可用性测试。

---

## 1. 什么是软件测试

一项**调查**,目的是向干系人提供关于被测产品质量的信息。质量维度:满足用户需求、符合需求、无错误与失效、适用性、客户满意度、付费意愿。

### 三种基本测试风格(以 LLM 文档 App 为例)

- **Happy path(正常路径)** — 用户按预期流程、用有效输入操作:上传符合限制的受支持 `.pdf`,App 成功解析并送给 LLM。
- **Edge case(边界情况)** — 极端但有效、处于正常行为边界的输入:
  - 文件大小恰好等于 Supabase 上限;文件名极长;文档打到 LLM 的上下文窗口上限;首次响应前快速连点"总结";上传中途离开页面再回来。
  - 相关 API 错误:`200 OK`、`400 Bad Request`(内容过滤/请求无效)、`429 Too Many Requests`(速率限制)、`500 Internal Server Error`。
- **Negative testing(负面测试)** — 系统应拒绝或优雅处理的无效输入与错误条件:不支持的文件类型(`.exe`、`.mp4`、`.zip`)、损坏的 PDF、超大小限制、调用 LLM API 时的异常、短时间内重复提交总结请求。

## 2. 缺陷、测试类型、成本

- 多项研究显示:**软件缺陷的主要来源是规格与设计** — 不是编码。
- **动态测试** — 以测试用例执行程序以检测缺陷。
- **静态测试** — 测试**未运行**的东西:审查代码与文档(需求规格、设计、用户手册、测试计划、测试用例)以定位错误。(非软件件也可能有 bug,应被测试。)
- **修 bug 的成本随发现时机越晚越高** — 尽早发现缺陷。

### 可验证(可测试)的需求

> 需求可验证,当且仅当存在某种有限且成本有效的流程,让人或机器能检查产品是否满足该需求。

- 不可验证:"运行良好""用户友好""通常会发生"。
- 可测试 NFR 示例:~~"医护人员容易使用"~~ → "医护人员接受四小时培训后应能使用系统所有功能;培训后,有经验用户的平均错误率不得超过每小时两次。"

### 缺陷移除效率(DRE, Defect Removal Efficiency)

- 好的测试流程应**增加测试者发现的缺陷数、减少客户发现的缺陷数**,并尽早检测。
- **DRE = (检测并移除的缺陷数) / (缺陷总数)**,其中总数 = 开发期间发现的 + **发布后第一年**报告的。
- 例:开发期间找到 1000 个 + 第一年报告 100 个 → 总计 1100。
- **练习**:A 团队测试中找 30 / 用户找 70(DRE ≈ 30%);B 团队找 20 / 30(DRE ≈ 40%)→ **B 更有效**,尽管总数较少。
- 每个阶段都可能注入*与*移除缺陷;测试主要负责移除 — 且修错缺陷本身可能引入新缺陷。

## 3. 手动 vs 自动化测试

### 手动测试

人类不使用自动化工具、手工执行测试用例(例:购物车示例 — 加 2× $19.99 + 1× $9.99 → 验证"3 items"与"$49.97")。

| 优势 | 劣势 |
|---|---|
| 可用性测试(界面是否直观) | 耗时 |
| 视觉验证(布局、颜色、响应式) | 易出错(人类计算失误) |
| 探索式测试(意外 bug) | 不可复现(不同测试者执行不同) |
| 整体 UX 感受与流畅度 | |

### 自动化测试

用软件控制测试执行。Agile 短周期使手动回归测试几乎不可能。**层级**(快/便宜 → 慢/贵):**单元测试 → service 层测试 → UI 测试**。

编写自动化测试的方式:**手写脚本**、**录制式**(工具捕获 UI 交互供重放)、**GenAI 辅助**(如 GitHub Copilot)。

## 4. 单元测试

- 以代码验证小型、隔离的单元(单个函数/方法)是否按预期。框架:**pytest**(Python)、**JUnit**(Java)、**Jest/Mocha**(JS)。
- **断言(assertion)** = 检查某条件为真的陈述;为假 → 测试失败。
- 示例(购物车:2× $19.99 + 1× $9.99):

```java
// JUnit — Arrange / Act / Assert
ShoppingCart cart = new ShoppingCart();
cart.addItem(2, 19.99);
cart.addItem(1, 9.99);
assertEquals(3, cart.getItemsCount(), "Cart should have 3 items after adding.");
assertEquals(49.97, cart.getTotalAmount(), 0.001, "Total amount should be 49.97");
```

```python
# pytest — 同一个测试
cart = ShoppingCart()
cart.add_item(2, 19.99)
cart.add_item(1, 9.99)
assert cart.get_items_count() == 3, "Cart should have 3 items after adding."
assert abs(cart.get_total_amount() - 49.97) < 0.001, "Total amount should be 49.97"
```

- **AAA 模式**:**Arrange**(准备对象、依赖、输入)→ **Act**(执行被测单元)→ **Assert**(验证实际 vs 预期)。
- **依赖与 flaky test**:等 IO/外部服务会杀死测试速度;依赖 live service/数据库/网络的测试会间歇性失败 → **flaky test** = 代码与环境未变但结果不一致。
- **Mock** — 模拟真实依赖行为的拟制对象:控制返回值、模拟错误,而不碰真实外部系统。

## 5. 集成测试

- 验证多个组件协同工作:REST API endpoints、业务逻辑、数据库。
- HTTP 是网页的请求/响应协议;REST API 通过 HTTP methods(GET、POST、PUT、DELETE)交换数据。
- **Mocking**:API 跑真实业务逻辑、写 app 自己的数据库,但**外部服务(如支付提供商)被 mock**,因为 app 不控制它们。

## 6. UI / 端到端测试(Playwright)

- **UI 测试**产生 UI 事件(按键、鼠标)并观察结果;**E2E** 在真实浏览器中测完整用户流程。
- **Playwright**(Microsoft,开源):驱动真实浏览器(Chromium、Firefox、WebKit)。
  - **Semantic locator(语义定位)** — 按用户认知找元素("标注为'Card Number'的字段""写着 'Pay' 的按钮")。
  - **Auto-waiting(自动等待)** — `expect` 断言会重试到超时。
  - **Happy path**:填支付表单 → API 验证/向 Stripe 收费 → 断言成功消息 + Order ID(证明后端已处理)。
  - **Unhappy path**:空表单 → 必填字段错误;用"declined"卡号 → UI 优雅处理 API 错误不崩溃。
  - **Mobile 布局**:程序化调整窗口尺寸;检查表单响应式、按钮不被裁切。
  - **Headed**(看着测试调试)vs **Headless**(无窗口;适合快速 CI/CD)。
- **Playwright + MCP**(Model Context Protocol):让 LLM 应用连接外部工具/服务的开放协议 — 让 AI 智能体以自然语言控制浏览器,不必每步写新脚本。
- **练习**:`git clone https://github.com/HKPolyUSE/playwright_testing`;在 IDE 配置 `@playwright/mcp` MCP server;跑登录 helper 示例(`doLogin` 用 `getByRole` locator)。

### UI 测试取舍

| 优势 | 限制 |
|---|---|
| 永远可自动化 | 比单元测试慢几个数量级 |
| 端到端覆盖(UI → services → DB) | 脆弱:标签从 "Submit" 改成 "Confirm" 就会打破 hardcode 选择器 |
| 适合高阶 **smoke test**(系统是否启动、部署、连线) | E2E 失败告诉你*有*问题,很少告诉你*在哪* |

### 自动化测试的整体好处

**快**(负载测试、大量随机测试)、**可靠**(每次操作完全相同,消除人类失误)、**可复现**(回归测试)。

## 7. 测试形状:金字塔 vs 甜筒

- **Ice cream cone(甜筒,反模式)**:大量手动测试 + 自动化集中在 UI 层;自动化只是在模拟慢速手动流程。
- **测试金字塔(Test pyramid)**:
  - **单元测试**(底) — 隔离的函数/方法;便宜、毫秒级、即时反馈。
  - **集成测试**(中) — 组件/services 协同:API endpoints、数据库操作、service 通信。
  - **UI/E2E 测试**(顶) — 通过 UI 的完整用户旅程。

## 8. 测试驱动开发(TDD)

- 常规流程:开发 → 写测试 → 跑测试。
- **TDD 循环**:写一个**失败**的测试 → 执行(失败)→ 写刚好让它通过的最少代码 → 执行 → **重构** → 重复(Red–Green–Refactor)。
- **"测试先行"是关于设计**:逼你先想清楚需求、设计 API/接口、决定代码如何使用。写得好单元测试是**运行中的规格**,也是技术文档的重要部分。
- **刚好够用的代码**:失败的测试标出了差距;只写让它通过的(实现可能非最优 — 之后重构)。
- **重构**:在不改变外部行为的前提下改进设计。
- **TDD 优势**:测试成为正确行为的契约;自动化测试每次 check-in 都跑;团队交付功能时不怕意外改动系统。附加价值:**约束 AI** — 测试限制 AI 的修改必须通过所有既有测试,防止它改坏正确的功能。

## 9. 可用性测试

- 测试用户使用界面的容易程度(在真实用户身上测试)。**五个维度**(Nielsen):**Learnability(易学性)、Efficiency(效率)、Memorability(记忆性)、Errors(错误:数量/严重度/恢复)、Satisfaction(满意度)**。
- **改善可用性**:邀约代表用户做真实任务;**观察**他们在哪停滞、犯错、困惑(不只靠印象);先修最大的问题;再测;在全部五维度上迭代。
- **Guerrilla testing** — 低成本、"野外"测试。
- **执行流程**:系统准备好停在起始页;facilitator 派发任务;询问思考过程;记录建议;让开发者/设计者观察;结束访谈(喜/厌、建议);产出**最终报告**(有效性、效率、任务时间、错误、满意度)。
- **受试者**:识别并招募(排期、地点、facilitator、记录员);**奖励**(免费午餐、礼品券)能提升出席率。
- **Usability lab**:简单单间 → 电子观察室。
- **Think-aloud(说出想法)**:受试者边做边口述思考;倾听他们做什么、找什么、觉得难在哪;温和提示("你现在在想什么?")。
- **测试设计**:
  - **Between-subjects(独立组)** — 每个部分由独特用户测试;缓解**学习迁移**(用过 A 会让 B 变简单),避免掩盖后期问题。
  - **Within-subjects** — 每个受试者测全部模块;用**counterbalancing**(随机/平衡任务顺序)+ 场次间休息。
- **收集数据**:
  - *绩效*:任务完成时间、正确完成率(有/无提示)、错误数、错误恢复时间、查手册次数、负面评论数。
  - *评分 + 理由*:有用性、符合预期、易用/易学/易设置/易无障碍、帮助质量。
  - *偏好 + 理由*:本原型 vs 另一原型、vs 竞品、vs 旧概念模型。

## 10. 重点 takeaway

- 测用户做的(happy path)、边界的(edge)、失败的(negative)— 三者都要。
- 多数缺陷源自规格/设计 → 早期静态测试(审查)是最便宜的缺陷移除。
- 需求必须可验证;用 DRE 度量你的流程。
- 自动化按金字塔形状:大量快速单元测试、较少集成测试、最少 E2E。
- mock 外部依赖以保持测试快而稳;避免 flaky test。
- TDD 把测试变成活规格 — 也是 AI 生成变更的护栏。
- 可用性要靠量测,不靠假设:观察真实用户、think-aloud、产出有证据的报告。
