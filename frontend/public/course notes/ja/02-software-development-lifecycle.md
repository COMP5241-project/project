# ソフトウェア開発ライフサイクル(SDLC)

> コース資料(57スライド)から抽出・整理したノート。要件、設計、実装、テスト、デプロイ、メンテナンス——Verification(検証)と Validation(妥当性検証)の違い、デプロイ戦略、デプロイ失敗のケーススタディを含む。

---

## 1. SDLC とは

ソフトウェア開発の各段階を示す構造化されたプロセス。**1970 年代**に大規模ビジネスシステムの管理のために開発され、今日も有効。

各段階:**要件分析 → システム設計 → 実装 → ユニットテスト → 統合テスト → システムテスト → 受入テスト → デプロイ → メンテナンス**。

## 2. 要件

### 機能要件 vs 非機能要件

- **機能要件**はシステムが*何を達成すべきか*を定義(例:「アカウント作成時に確認メールを送信」「検索バーでクエリを入力して項目を検索」「チェックアウト前にカート内の項目を確認・数量変更・削除」「SNS ログイン」「通知」「評価/フィードバック」)。
- **非機能要件**はシステムが*どれだけ良く動くか*を定義(性能、セキュリティ、可用性など)。

### 機能要件の収集

| 手法 | 目的 |
|---|---|
| ドキュメント分析 | 既存の業務プロセス/システムを確認し、要件を特定 |
| 観察 | 利用者が実際の環境で働く様子を観察(ワークフロー、ペイン) |
| インタビュー | ステークホルダーとの 1 対 1 の深い対話 |
| アンケート・質問票 | 大規模な定量データ収集 |
| フォーカスグループ | 多様なステークホルダーの視点収集 |
| プロトタイピング | 早期バージョンを作り、要件を可視化してフィードバックを得る |

AI が補助できる(例:Zoom 会議を要件要約に)——ただし**必ず AI の出力が正しいか確認し、磨き上げた上でクライアントと確認すること**。

### 要件エライシテーションと管理

- **エライシテーション**:ステークホルダーを特定 → 情報収集(インタビュー、アンケート、ワークショップ)→ ドキュメント化。
- **管理**:優先順位付け(最も必須なものを先に);変更管理(変更を管理下に置きスコープクリープを防ぐ);検証と妥当性確認(システムが特定された要件すべてを満たすこと、かつそれらが本来の目的を果たすこと)。

### 課題と対策

課題:ステークホルダーがニーズを明確に伝えられない;優先順位や前提の衝突;ビジネスニーズの時間経過による変化・揺れ。

- **より良い質問をする**:解ではなく問題から始める(「何を解決したい?ビジネス価値は?」);オープンでプロセス重視の質問(「今はどうやっている?何が壊れる?判断に必要な情報は?」);前提に疑問を投げかける(「データが欠落したら?例外は?誰が決裁か?」);**5 Whys** で症状ではなく根本原因を。
- **統合・明確化・衝突解消**:セッション中に言い換え確認(「私の理解では……それで合っていますか?」);曖昧な記述をテスト可能で具体的な要件/ビジネスルールに変換;**MoSCoW**(Must/Should/Could/Won't)で「今必須 vs 後回し」の合意形成。

## 3. プロトタイプと MVP

- **ワイヤーフレーム** — Web/App の低忠実度の構造図。**モックアップ** — 静的だが最終製品に近しい見た目(ブランド、色、フォント、アイコン)。**高忠実度プロトタイプ** — 最終製品に最も近く、見た目とユーザーフローの両方をテスト可能。
- **タイプ**:使い捨て(迅速にフィードバックを得て要件を磨き、使ったら捨てる)/ 進化型(フィードバックで逐次磨き上げ最終版へ)/ 増分型(最終製品を部品に分割し、個別開発して最後に統合)。
- 「私が何想要的かは言えない。でも見たらわかる。」

### MVP(Minimum Viable Product)

- 独自で不確かなものを構築する時は市場検証が重要:**最小の努力で、最大量の検証済みユーザー学習**を得る。Minimum = 時間と努力を最小化;Viable = ユーザーが使ってくれるかどうかを正確に評価できる品質。
- 実際のユーザーでアイディアを検証 → 主要価値指標を収集 → 次の MVP を作る、という循環。経済的に成立しない製品を作るリスクを低減。

| 観点 | プロトタイプ | MVP |
|---|---|---|
| 目的 | コンセプト・デザイン・UX のテストと可視化 | ユーザーにコア機能を提供 |
| 機能 | 非機能または機能限定の場合が多い | コア機能が完全に動く |
| 市場準備 | 市場に出せない | 市場に出せる |
| フィードバック焦点 | デザインと実現可能性の初期フィードバック | 製品価値と使いやすさの実ユーザーフィードバック |
| 開発段階 | 初期、本開発の前 | 初期リリース、最初の使える版 |
| ゴール | デザイン・技術実現可能性の検証 | ビジネスアイデアの検証・ユーザー獲得 |

## 4. 設計と実装

- 要件は**何を(what)**するかを述べ、設計は**どのように(how)**実装するかを述べる。
- **システムデザイン面接**:候補者にホワイトボード/仮想キャンバス上でスケーラブルなシステムを設計させる技術評価——要件、トレードオフ、コンポーネント間相互作用の推論能力を見る。
- **例:GenAI チャットアプリ** — Python Flask API バックエンド(ビジネスロジック、データ格納/取得;フロントエンドからの質問を受け AI サービスへ渡し回答を返す)+ React フロントエンド(質問入力・回答表示の UI;API リクエストで質問を送りレスポンスを表示)+ OpenAI Azure サービス(GenAI API が言語モデルで回答)+ データベース(過去のチャット保存)。
- **API キーの保護:**
  - 開発時:秘密キーは `.env`(ローカル環境変数)に保存;`.gitignore` で `.env` と機密ファイルをバージョン管理から除外。**秘密キーはリモートリポジトリに一切載せてはならない。**
  - 本番時:キーはオンラインプラットフォーム(例:Vercel の環境変数設定)に安全に保存し、デプロイ時に実行中のアプリへ注入。公開とフロントエンドコードからは隠される。

## 5. テスト段階

- **ユニットテスト**:個別ユニット(手続き、関数、メソッド、クラス)をユニット設計仕様に基づき**隔離してテスト**;障害の特定が容易。
- **統合テスト**:モジュールを組み合わせてグループでテスト——モジュール単体は正しくても、2 つ以上のモジュールを統合した際にバグが発生しうる(例:呼び出し側が被呼び出し側のインターフェース仕様が誤解している)。
- **システムテスト**:システムが要件仕様の全要件を実装しているかを検証——機能性(必要な全機能の実装)、堅牢性(エラー状態からの復旧)、相互運用性(サードパーティシステムとの連携)、性能(スループット、レスポンスタイム)、スケーラビリティ(スケール増大時の挙動、例:ユーザー数)、信頼性(長期間の安定稼働)、ドキュメントテスト(ユーザーガイドの正確性と使いやすさ)。
- **Pull Request(PR)**:あるブランチの変更を別ブランチにマージすることを提案し、統合前にチームが議論・レビュー・承認するワークフロー。
- **確認テスト(Confirmation)**:前回失敗したテストケースを再実行し、修正が成功したことを検証。
- **回帰テスト(Regression)**:変更(バグ修正や機能追加)後、以前テスト済みのプログラムを再テストし、変更した領域以外に缺陷が入っていないことを保証。全テストケースを再実行(自動化が有効——マイクロソフトは**全 PR で 6 万超のユニットテストを 7 分未満で実行**)、または変更されたステートメント/モジュールに関わる部分集合を選ぶ。
- **テスト自動化**:ソフトウェアでテスト実行を制御;ユニットテストはコード(メソッド)が期待通りに動作するかを確かめるコード(例:Java の JUnit)。
- **受入テスト**:顧客/エンドユーザーが受入基準(機能、性能、セキュリティなど)に基づきシステムが「正しいもの」を作られたかを検証。
  - **αテスト(Alpha)**:開発者のサイトで行い、開発者が立ち会う。
  - **βテスト(Beta)**:開発者不在の複数ユーザーサイトで行う——実際の使用に最も近い。

### Verification(検証)vs Validation(妥当性検証)

- **Verification(検証)** — 最終製品を**正しく**作っているか(「product right」)の評価。例:コードレビュー、ユニット/統合/システムテスト;通常は開発者が行い、仕様に合致し正しく実装されていることを保証。
- **Validation(妥当性検証)** — ソフトウェアがユーザー/ビジネスのニーズを満たし、**正しい**製品を作っているかの評価(「right product」)。例:プロトタイピング、受入テスト、ユーザビリティテスト、本番テスト、A/B テスト。
- Validation はソフトウェアを改良する**新しい要件**を生み、フィードバックループを形成。

## 6. デプロイと環境

- ソフトウェアは顧客環境にデプロイされ、または市場/本番にリリースされる。
- **Dev vs Production の差異**:OS バージョン・ライブラリが異なる;本番データには開発環境にないエッジケースやデータ量;より厳格なアクセス制御やファイアウォール;異なるリソース制限;依存するライブ外部サービスの挙動が異なる。「自分の環境では動く」≠「本番で動く」。

## 7. メンテナンス

- 本番へのデプロイ**後**のソフトウェア製品の変更:本番のバグ・問題修正、パッチリリース、製品・性能の強化、機能強化版の新リリース。
- **60/60 ルール**(IEEE Software, 2001):メンテナンスは平均して**ソフトウェアライフサイクルコストの 60%**;メンテナンスの約 60% は、システムを止めずに壊さずに新機能を追加すること。クリーンスレート(ゼロから設計)プロジェクトでは、メンテナンスの方が開発より難しいことが多い。
- **ISO/IEC 14764:2006** のメンテナンスタイプ:**Corrective(是正)**欠陥の修正;**Adaptive(適応)**変化する環境との互換性維持;**Perfective(完全化)**性能・保守性の向上;**Preventive(予防)**潜在問題を先回りで処理。

### デプロイ失敗ケーススタディ

- 午前 1:00:新機能デプロイ完了。即時のヘルスチェックは全通過、システムは安定に見える。
- 午前 3:00:新クエリが連鎖的に開始、レスポンスタイムが大幅に悪化——事故の開始だが**アラートはなし**。
- 午前 10:00:事故を発見——7 時間、アプリは事実上使えない状態だったのに、運用チームは知らなかった。
- 調査:アプリと DB のログからアプリサーバのリソース枯渇と高レイテンシが判明;午前 1:00 のデプロイと相関 → **根本原因**:新機能が適切なインデックスを持たない非効率なクエリを持ち込み、リソースをロックしてシステム全体を遅くしていた。
- 対処:問題クエリの書き直しと必要なインデックス追加;patch v1.1 をまず staging 環境でテスト(レスポンスタイム改善、エラーなし)、その後本番デプロイ;リアルタイム指標で DB ロード低下を確認。**夜 9:00 にサービス回復**、事故は性能劣化開始から 18 時間で正式クローズ。

| 指標 | 定義 | 本ケース |
|---|---|---|
| **TTD**(Time to Discover) | 障害開始 → チームが認識 | 7 時間(午前 3 時 → 午前 10 時) |
| **TTM**(Time to Mitigate) | チームの運用速度:診断、修正、検証 | 約 8 時間(クエリ最適化の複雑さが主導) |
| **TTR**(Time to Recover) | 顧客への総影響時間 | 18 時間(午前 3 時 → 夜 9 時) |

## 8. 可用性

- **可用性 = Uptime / (Uptime + Downtime)** = MTTF / (MTTF + MTTR)。「9」の個数で表現:

| Uptime | 週あたり停止 | 月あたり停止 | 年あたり停止 |
|---|---|---|---|
| 99% | 1.68 時間 | 7.2 時間 | 3.65 日 |
| 99.9% | 10 分 | 43.2 分 | 8.76 時間 |
| 99.95% | 5 分 | 21.6 分 | 4.38 時間 |
| 99.99% | 1 分 | 4.32 分 | 52.56 分 |
| 99.999% | 6 秒 | 26 秒 | 5.26 分 |

- 可用性に影響する要因:ハードウェア故障、ネットワーク不安定、ソフトウェアバグ、メンテナンス停止、サイバー攻撃(DDoS、マルウェア)、停電、容量オーバーロード、設定ミス、サードパーティ障害、バックアップ/復旧の不備。

## 9. デプロイ戦略

| 戦略 | 仕組み | トレードオフ |
|---|---|---|
| **Big Bang** | 新版本を一気に展開(サービス停止を伴う);失敗すれば旧版へロールバック | 公開・業務クリティカルなアプリにはリスク高;リリース前の十分な開発テストが必要;停止中かつロールバックが困難 |
| **Rolling upgrade(ローリング)** | 新版本が旧版本を徐々に置換;新旧が共存する期間がある | 旧コンポーネントと非互換の新コンポーネントをロールバック可能 |
| **Blue-Green(ブルーグリーン)** | 同一の本番環境を 2 つ保持;Blue が全トラフィックを受信;Green に新版本をデプロイし機能・性能をテスト;合格後にトラフィックを Blue → Green に切り替え | Green が本番になってから問題があれば、トラフィックを Blue に戻して即ロールバック |
| **Canary(カナリア)** | 小さなインスタンス数のみ新版本にアップグレード;ユーザーの一部をカナリアインスタンスへルーティング;エラーがなければ段階的に全体へ | 新版本の本番投入リスクを低減 |
| **Feature flag(フィーチャーフラグ)** | **新コードのデプロイなし**で特定機能の可視性・有効化を制御 | リリースとロールアウトを分離 |

### ビッグテックがコードを本番に出す方法

1. 開発中は Git で定期コミットし、全変更を追跡。
2. コミットされると **CI/CD** サーバ(例:CircleCI)が引き継ぎ:自動ビルド、ユニットテスト、品質チェック。
3. 本番前に独立した **QA 環境**へ移動し、QA チームが回帰・性能チェック。
4. 本番リリースにはフィーチャートグル、カナリアデプロイ、A/B テスト等の戦略とツールを使用。
5. **モニタリングと信頼性**:SRE が Prometheus、Datadog 等の監視ツールでシステム性能を密注し、問題を即時解決。

## 10. キーポイント

- 要件の品質が下流すべてを決める;エライシテーション技法、MoSCoW、5 Whys を活用。
- プロトタイプはデザインを検証、MVP はビジネスアイデアを検証。
- Verification = 製品を正しく作る;Validation = 正しい製品を作る。
- バグは早期発見ほど安価;階層別テスト(ユニット → 統合 → システム → 受入)。
- デプロイはリスク管理の演習;クリティカル度とロールバック要件で戦略を選択。
- メンテナンスがライフサイクルコストの大半(60/60)——設計段階から考慮。
- 本番は別環境:異なるデータ、制約、依存を想定。
