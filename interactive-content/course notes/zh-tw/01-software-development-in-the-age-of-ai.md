# 人工智慧時代的軟體開發

> 整理自課程簡報(83 頁)。涵蓋 AI 如何重塑軟體開發:Vibe Coding(氛圍式編程)、Agentic Coding(代理式編程)、生產力實證、風險,以及現在重要的技能。

---

## 1. AI 輔助編程的崛起

- Stack Overflow 2025 開發者調查勾勒了當前 AI 開發的景觀。
- NVIDIA 執行長黃仁勳(Jensen Huang)認為,透過自然語言互動,AI 將讓每個人成為「程式設計師」。
- 真實案例:一名不懂程式碼的人用 12 天開發出含前端、後端、資料庫的完整軟體;微軟執行長表示 AI 撰寫了最多 30% 的程式碼,有些專案甚至全部由 AI 撰寫;Anthropic 執行長曾預測一年內所有程式碼都將由 AI 生成。
- **AI 在 SDLC 各階段的應用:**
  - **發現(Discover)**——快速理解與導覽陌生或新穎的程式碼庫。
  - **設計(Design)**——規劃與架構的思考夥伴:提出多套實作方案、重構策略、修復計畫;撰寫技術規格。
  - **建構(Build)**——實作程式碼、撰寫並執行單元測試、起草 commit 與 PR 訊息。
  - **部署(Deploy)**——自動化 CI/CD、設定環境、管理發布。
  - **支援與擴展**——診斷錯誤、分析日誌、比手動除錯更快提出修正;輔助大規模重構。
- **工具景觀**:消費級(Replit、v0、Lovable、bolt…)與開發者級(GitHub Copilot、Cursor、Windsurf、Claude Code、Antigravity、Trae、Opencode),以及設計工具(Figma、Google Stitch)。

## 2. Vibe Coding(氛圍式編程)

- 由 **Andrej Karpathy** 提出:「完全順從氛圍、擁抱指數成長、忘了程式碼的存在」。出錯時直接把錯誤訊息貼回去,通常就修好了。
- 實作者以**結果**導向,而非逐行審查。
- 已進入企業:例如台灣餐廳科技公司 iCHEF 一名無工程背景的業務與營運總監,用 Gemini 建置了多個內部 AI 小工具。
- Agentic Coding 讓原型開發從數週縮短到數分鐘/數小時。

## 3. 從 LLM 到自主代理(Agent)

三層自主程度:

| 層級 | 說明 |
|---|---|
| 1. 反應式 | 純被動回應;需要人類逐步指示;只能產生答案,無法代替你完成任務 |
| 2. 協作式 | 與人協作達成目標;能處理複雜提示、提出想法、自動化部分工作流,但仍依賴人類的方向、回饋與最終核准 |
| 3. 自主式 | 高度自主;人只給高階目標,代理自行決定步驟、使用其他軟體/工具,全程無需持續人工干預 |

**自主性階梯(從自動補全到自主):**

1. 自動補全 — 編輯器內的 token 預測
2. 內聯建議 — 由函式簽名生成整個函式
3. 對話式生成 — 用自然語言描述功能,取得可運作的程式碼
4. 編程代理 — 多檔案編輯、工具使用、跑測試、自我修正迴路
5. 自主代理 — 複製 repository、在沙箱中規劃、跑測試、提交 PR

## 4. 編程代理如何運作

- 三個階段:**收集上下文 → 採取行動 → 驗證結果**。
- 工具家族:檔案操作(讀/改/建/重命名)、搜尋(glob、regex、探索程式碼庫)、執行(shell、伺服器、測試、git)、Web(搜尋、抓文件、查錯誤)。
- 示例:「修復失敗的測試」→ 跑測試套件 → 讀取錯誤輸出 → 搜尋相關檔案 → 閱讀程式碼 → 編輯修改 → 重跑測試驗證。
- **上下文視窗**:容納本次 session 的一切(指示、讀過的檔案、代理自己的回應)。**子代理(subagent)**在獨立的上下文視窗中執行,大型檔案讀取不佔用主視窗;只傳回摘要與少量元數據。

## 5. Harness Engineering(代理框架工程)

- OpenAI 案例:**3 名工程師、5 個月、約 100 萬行程式碼,0 行由人手撰寫**——應用邏輯、測試、CI 設定、文件、工具全數由 Codex 產生。「人類掌舵,代理執行。」
- 「軟體工程團隊的首要工作不再是寫程式碼,而是設計環境、明確意圖、建立讓 Codex 代理可靠工作的回饋迴路。」

| 概念 | 管控範圍 |
|---|---|
| **Prompt Engineering(提示工程)** | 你說了什麼:措辭、結構、system/user prompt、few-shot 範例 |
| **Context Engineering(上下文工程)** | 模型看到什麼:程式碼庫、架構、慣例、意圖等豐富結構化資訊 |
| **Harness Engineering(代理框架工程)** | 整個代理系統如何運作:工具、防護欄、回饋迴路、可觀察性、版本管理、錯誤恢復 |

> **Agent = Model + Harness(代理 = 模型 + 框架)。**

## 6. AI 生成程式碼的已知失敗模式

- **紫色按鈕問題**:Tailwind 的 `bg-indigo-500` 在教學、範例專案、開源專案中出現頻率過高,AI 從統計上把「按鈕/現代 UI」與這個紫色聯結——AI 生成的 UI 預設偏紫色。
- **Vibe coding 應用的安全事件:**
  - 一位「氛圍程式員」的 AI 建置 SaaS(「零手寫程式碼」)遭攻擊:訂閱被繞過、API key 被耗盡、資料庫被破壞。
  - Tea(女性專用交友 App):後端 Firebase 完全無認證開放 → **72,000 多張私人圖片與 13,000 多張政府簽發身分證件外洩**;批評者歸咎於未經審查的 AI 生成程式碼。
- AI 程式碼常見安全漏洞:登入無速率限制、API key 未保護、管理功能只靠前端路由防護、從前端操弄資料庫。
- **70% 問題 / 最後一哩**:前 70%(模式化、框架標準的程式碼)來得飞快;最後 30%——邊界情況、架構打磨、可維護性——陷入報酬遞減,需要扎實的人類專業。
- AI 提升了**產出**,但也增加了**返工**;GitClear 發現 2024 年 5 行以上重複程式碼塊的頻率是 2022 年的約 8 倍。AI 的修改傾向*新增*程式碼,而非移動/更新/刪除既有程式碼。

## 7. 生產力實證

- **軟體工程最難的部分是理解需要建構什麼**——「我 80% 的工作是填補規格與現實之間的巨大落差」。
- **Stanford 研究(約 10 萬名開發者、27 家公司、136 個團隊):**
  - **Greenfield(全新程式碼庫,低複雜度)**:生產力 **+30–40%**。
  - **Brownfield(大型、成熟程式碼庫,高複雜度)**:增益僅 **0–10%**。
  - 程式碼庫越大,AI 效果下降越明顯:上下文視窗限制、「訊噪比」問題、領域特定邏輯;即使 SOTA 模型,長上下文下效能也會下滑(例:32k tokens 時從 90% 掉到 50%)。
- **Brownfield 就像「屋主還住在裡面時重新裝修廚房」**——不能斷水斷電,拆牆改管必須極其精準。
- 真實世界的編程很混亂:把模糊的商業需求轉譯成可用軟體;管理預期、理解複雜 legacy 系統、應對不可預測的人為因素。AI 的短板:上下文視窗(10萬–20萬 tokens)只占中等程式碼庫的一小部分;真實系統有複雜依賴(資料庫、API、微服務、腳本、跨團隊知識);難懂業務規則、邊界情況、人為例外;無法輕鬆拉人協作以釐清需求;隱性狀態與基礎設施複雜度(快取、訊息佇列、session 儲存、散落各處的設定)——可能在不了解關鍵基礎設施依賴的情況下建議重構。**AI 在需要深度上下文知識的混亂真實場景中會失敗**;開發者仍需提供上下文、方向與品質控制。

## 8. 勞動與職業影響

- Anthropic 警告:AI 可能在 1–5 年內淘汰 50% 的白領入門職位;Salesforce 宣布 2025 年不再新聘軟體工程師。
- **初級開發者危機**:AI 最擅长的任務(樣板碼、簡單 bug、測試生成)正是初級工程師的練兵場。讓初級者跳過「掙扎」,等於剝奪從第一性原理學習的機會。如果現在停止招聘/培訓初級者,未來會出現無人真正理解系統、AI 失敗時無人能除錯的危機。
- 實習生案例:AI 出現前,把任務委派給實習生,經理要先想清楚問題、寫需求/背景/技術規格,再交接、反覆跟進、澄清、審查;有了 AI,經理把需求與設計想清楚後,直接交給 AI 實現、測試、迭代,往往比完整的實習生委派週期還快。當「執行」越來越多由 AI 承擔,對實習生真正有價值的技能不再是執行定義良好的任務,而是**學會自己定義、劃定範圍、推理問題**。
- AI 讓編程成為**基礎技能**:過去寫程式碼是程式設計師價值的主要來源;現在 AI 非常擅長把清晰需求變成能跑的程式碼。不懂寫程式碼肯定行不通,但*只*會寫程式碼也不夠了。

### 新角色與組建元件

- **AI 工程師**(借助 AI API 與開源模型構建應用)vs **ML 工程師**(構建 AI API/模型本身)。要求:扎實的軟體工程基礎;構建可靠、可擴展應用的能力;熟悉現代 AI 工具與框架;關注使用者體驗與實際應用。
- 除了會呼叫 LLM API,還需廣泛掌握組建元件:提示技術、代理框架、**評估(evals)、防護欄(guardrails)、RAG、語音棧、非同步程式、資料抽取、向量資料庫、微調、圖資料庫 + LLM、代理式瀏覽器/電腦操作、MCP、推理模型**……
- **2023 vs 2026 求職市場**:2023 = 學 HTML/CSS → 做示範專案 → 應徵。2026 = 系統設計 + 雲基礎設施 + DevOps + 網路 + 效能優化 + 溝通 + LLM API + AI 代理 + 提示/上下文工程……+ 做出真實專案,在成千上萬的申請者中脫穎而出。
- **Zara Zhang**(人文背景的非技術 builder):用 Claude Code 等編程代理端到端交付真實產品,累計 30k+ GitHub stars(其中 5+ 個專案 1,000+ stars);她認為編程正從*職業*變成像寫作一般的*通用技能*——商業主、行銷、PM、設計、創作者都能受益;人文背景的人尤其被需要:察覺真實使用者需求與痛點、從個人挫敗/對話/回饋中獲得點子、理解人而不只是技術(他們的掙扎、場景、job-to-be-done)、判斷「好」與「更好」。

## 9. 人類新價值:從「做」到「定義」

- **HBR**:「AI 讓建構變容易,選擇建構什麼更難。」AI 擅長執行,不擅長出點子。當 AI 承擔更多「怎麼做」,人類就要對「做什麼」與「為什麼」負更多責任。先把問題定義到能做出粗糙原型,再用原型打磨問題。評估原型看它引發了什麼問題,而非看起來多完整。
- **產品思維**:以整個產品生命週期中使用者與業務的結果思考與行動,而不是只完成任務/功能。
- **開發中的產品思維**:主動理解使用者動機、痛點、工作流,而不只是讀需求文件;看到改動對整個產品與生態(效能、UX、可維護性)的影響;實作前問「我們在解決什麼問題?」「這是最好的解法嗎?」;理解產品如何賺錢、成功長什麼樣、決策如何影響成本/營收/競爭力;用簡單語言向 PM、設計、持份者解釋取捨與技術約束;質疑模糊需求、提出替代方案。
- **FireCut 案例**(Premiere Pro / DaVinci Resolve 的 AI 影片剪輯外掛):
  - Suhail 收集了 50+ 個他遇到或聽到抱怨的問題;用 4 個問題過濾點子:*問題夠痛嗎?使用者付得起錢嗎?我能觸達他們嗎?市場在成長嗎?*
  - **不對稱優勢**:不只是會寫程式,還有劍橋同學 Ali Abdaal(YouTuber)的剪輯團隊(潛在 beta 使用者)、商業經驗、創作者分發渠道。能採訪真實剪輯師、觀察工作流、快速測試 → 最終做成了 Premiere Pro 外掛,而非獨立 web app(剪輯師就在 Premiere 裡工作,不想上傳大文件)。**「不要基於假設設計,要觀察人們如何工作。」**
  - **最小原型**:第一版只做一件事——自動偵測並刪除停頓。約兩天用 Python/JS + GPT-4 搭出粗糙原型,程式碼很亂但足以測試概念。約 200 人註冊、20 人測 beta;六週幾乎每天迭代,而不是私下猜幾個月。使用者告訴他哪些功能重要、哪裡困惑、哪裡失敗、為何流失。前期他一人身兼產品/調研/行銷/銷售/支持/營運;月營收到 ~$30,000 才招專業工程師、擴展團隊。
- **「建構」變容易了,「注意力」沒有變多**:AI 工具讓開發變快,但不會創造更多人的注意力與信任;能上線產品的人變多,競爭加劇,被看見更難。
- **餐廳選單比喻**:AI 設計餐廳選單可以立刻看起來很精緻,但「這是對的選單嗎?顧客會喜歡這些菜嗎?設計符合品牌嗎?」——**「選單可以很好看,但可能仍是錯的選單。這件事沒有測試可做。」**AI 降低了執行的成本;方向與判斷來自人。
- **品味(taste)**:「代理可以告訴你一個東西看起來正確、符合規格——但不代表它*好*。好,可以是使用者體驗層面的好、令人愉悅、讓人願意回來。模型要完全接住這種細膩度還需要時間。即便一兩年後模型追上了,工程師仍需對這些系統負責——這需要理解系統、別人信任你、你有專業積累,不是一夜之間的事。」

### 新瓶頸:審查容量

- 產生程式碼很容易;**驗證才是差異化**:寫好測試(unit/integration/e2e)、批判性地讀程式碼、系統性地除錯。
- **架構師的崛起**:不再以寫了多少行程式碼來評判你,而是評判你**規格說明的清晰度**與**驗證的嚴謹度**。

### 從 Vibe Coding 到 Agentic Engineering

| 面向 | Vibe Coding | 結構化 AI 輔助編程 | Agentic Engineering |
|---|---|---|---|
| 意圖 | 隨口的自然語言提示 | 帶範例與約束的詳細提示 | 正式規格、架構文件、記憶檔案 |
| 驗證 | 「看起來能跑嗎?」 | 手動測試、抽查 | 自動化測試套件、CI/CD 閘門、LLM 評審 |
| 程式碼庫理解 | 極少;可能根本不讀生成的程式碼 | 選擇性審查關鍵路徑 | 全面審查架構;AI 處理實作細節 |
| 錯誤處理 | 把錯誤訊息貼回給 AI | 開發者診斷根因,AI 實施修復 | 代理在既定邊界內自我診斷;人處理架構問題 |
| 適用範圍 | 原型、腳本、個人專案、黑客松 | 既有程式碼庫中的功能 | 生產系統、團隊級開發 |
| 風險 | 高;一次性程式碼可接受 | 中;關鍵節點有人類判斷 | 低;每個階段系統性驗證 |

## 10. AI 時代的必備技能

1. **知道建構什麼、為什麼重要**——這個需求服務於什麼目標?它真的重要嗎?使用者的真實問題是什麼?哪些功能值得做?
2. **從實作者到編排者(orchestrator)**——你不只是寫程式碼的人了;人類的核心角色是編排寫程式碼的 AI 代理、評估其產出、提供策略方向、確保系統為正確的持份者解決正確的問題。
3. **設計與拆解**——系統該如何設計?有沒有更簡單的方案?工作如何拆解?哪些部分 AI 能處理、哪些需要我的判斷?
4. **判斷 AI 產出是否可用**——程式碼審查:為什麼這樣寫?正確、靈活、可維護嗎?改動會影響既有程式碼庫的正常運作嗎?基於業務語境有沒有更好的設計?極端流量下會崩嗎?如何測試災難性失敗?
5. **發現隱藏問題**——未處理的邊界情況、權限洩漏、效能瓶頸、隱藏漏洞、技術債,趕在進生產環境之前。
6. **開發與維護生產級應用與大型程式碼庫**,服務數千(或更多)真實使用者;理解程式碼上線後會發生什麼:可靠性、安全性、穩定性、事故、長期維護成本。
7. **產品與持份者技能**——與持份者互動識別痛點、對原型收集回饋、迭代改進;構建真正有用、持份者願意用、願意付費、願意推薦的系統。**「持份者技能」已是核心工程技能**:和持份者(使用者、客戶、業務主)談,理解他們的真實問題;深刻理解使用者、能轉譯為精確代理指示的工程師,價值遠超他人。

> 雖然 AI 能自動化(大部分)編程任務,但構建一個真正有用、上線後穩健可擴展、被大量使用者可靠使用的軟體產品,絕非易事!

### 保持競爭力

- 現在用 AI 做出「平庸」原型很容易——**平庸在 AI 時代不再夠用**。
- **GitHub 即履歷**:鼓勵用 AI 構建工具、寫程式碼、組織知識,並把專案發布到 GitHub/YouTube。一個 3,000 stars、被數百人使用的專案,雇主要求可被真實影響取代入門經驗而錄取。
- 提升溝通與表達能力;培養品味與判斷力。

### 以學習心態使用 AI

- AI 給出答案時,追問「為什麼」;
- 自己完成任務/從零構建(不用 AI)來打基礎;
