# ソフトウェアテスト概論

> コース資料(60スライド)から抽出・整理したノート。テストの基礎(happy path / エッジ / ネガティブ)、静的 vs 動的テスト、DRE、テストピラミッド、unit/integration/UI テスト(Playwright 含む)、TDD、ユーザビリティテスト。

---

## 1. ソフトウェアテストとは

テスト対象の製品/サービスの**品質についてステークホルダーに情報を与える調査**である。品質の側面:ユーザーのニーズ充足、要件適合、エラー/故障の不在、適用性、顧客満足、支払意欲。

### 基本的な 3 つのテストスタイル(LLM ドキュメントアプリを例に)

- **Happy path(正常系)** — ユーザーが意図したワークフローで有効な入力を使うとき:サイズ制限内の対応 `.pdf` をアップロードし、アプリが正常にパースして LLM に送信。
- **Edge case(エッジケース)** — 極端だが概ね有効で、正常動作の境界にある入力:
  - Supabase の最大ファイルサイズちょうど;非常に長いファイル名;LLM の最大コンテキストウィンドウに到達する文書;最初の応答前に「要約」を高速連打;アップロード中にページを離れて戻る。
  - 関連 API エラー:`200 OK`、`400 Bad Request`(コンテンツフィルタ/無効なリクエスト)、`429 Too Many Requests`(レート制限)、`500 Internal Server Error`。
- **Negative testing(ネガティブテスト)** — システムが拒否または適切に扱うべき無効入力・エラー条件:非対応ファイル形式(`.exe`、`.mp4`、`.zip`)、破損 PDF、サイズ超過、LLM API 呼び出し時の例外、短時間での要約リクエスト連続送信。

## 2. 欠陥、テストタイプ、コスト

- 多くの研究が示す:**ソフトウェア欠陥の主因は仕様と設計** — コーディングではない。
- **動的テスト** — テストケースでプログラムを実行して欠陥の存在を検出。
- **静的テスト** — **実行しないもの**をテスト:コードとドキュメント(要件仕様、設計、ユーザーマニュアル、テスト計画、テストケース)をレビューして誤りを発見。(ソフトウェア以外でもバグがあり得る。)
- **バグ修正コストは発見が遅いほど高くなる** — 早期に検出。

### 検証可能(テスト可能)な要件

> 要件が検証可能であるとは、人間や機械が製品が要件を満たすかをチェックできる有限で費用対効果のあるプロセスが存在すること。

- 検証不能:「よく動く」「使いやすい」「通常は起きる」。
- テスト可能な NFR の例:~~「医療スタッフが使いやすい」~~ → 「医療スタッフは 4 時間の訓練後、システムの全機能を使えること。訓練後、経験あるユーザーの平均エラー数は 1 時間あたり 2 個を超えないこと。」

### Defect Removal Efficiency(DRE:欠陥除去効率)

- 良いテストプロセスは、**テスト者が見つけた欠陥を増やし、顧客が見つけた欠減を減らし**、できるだけ早期に検出する。
- **DRE = (検出・除去した欠陥数) / (欠陥総数)**。総数 = 開発中に発見した + **リリース後 1 年目**に報告された。
- 例:開発中 1000 件 + 1 年目 100 件 → 総計 1100。
- **演習**:A チームはテストで 30 / ユーザーで 70 発見(DRE ≈ 30%);B チームは 20 / 30(DRE ≈ 40%)→ **B の方が有効**(総数が少ないのに)。
- 各フェーズは欠陥を注入*し*除去しうる;テストは主に除去を担当 — ただし誤った修正自体が新規欠陥を生みうる。

## 3. 手動 vs 自動テスト

### 手動テスト

人間が自動化工具なしでテストケースを手動実行(例:カート — 2× $19.99 + 1× $9.99 を追加 → 「3 items」と「$49.97」を確認)。

| 強み | 弱み |
|---|---|
| ユーザビリティテスト(インターフェースの直感性) | 時間がかかる |
| 視覚検証(レイアウト、色、レスポンシブ) | 人間エラー(計算ミス) |
| 探索的テスト(予期せぬバグ) | 再現性なし(テスト者によって実行が異なる) |
| 全体の UX の感触と流れ | |

### 自動テスト

ソフトウェアでテスト実行を制御。アジャイルの短いサイクルでは手動回帰テストはほぼ不可能。**レイヤ**(速い/安い → 遅い/高い):**ユニットテスト → サービスレイヤテスト → UI テスト**。

自動テストの書き方:**ハンドスクリプト**(テストコードを直接書く)、**記録式**(ツールが UI 操作をキャプチャしてリプレイ)、**GenAI 支援**(例:GitHub Copilot)。

## 4. ユニットテスト

- 小さい隔離されたユニット(単一の関数/メソッド)の正しさを検証するコードベースのテスト。フレームワーク:**pytest**(Python)、**JUnit**(Java)、**Jest/Mocha**(JS)。
- **アサーション** = 特定条件が真かをチェックする文;偽 → テスト失敗。
- 例(カート:2× $19.99 + 1× $9.99):

```java
// JUnit — Arrange / Act / Assert
ShoppingCart cart = new ShoppingCart();
cart.addItem(2, 19.99);
cart.addItem(1, 9.99);
assertEquals(3, cart.getItemsCount(), "Cart should have 3 items after adding.");
assertEquals(49.97, cart.getTotalAmount(), 0.001, "Total amount should be 49.97");
```

```python
# pytest — 同じテスト
cart = ShoppingCart()
cart.add_item(2, 19.99)
cart.add_item(1, 9.99)
assert cart.get_items_count() == 3, "Cart should have 3 items after adding."
assert abs(cart.get_total_amount() - 49.97) < 0.001, "Total amount should be 49.97"
```

- **AAA パターン**:**Arrange**(オブジェクト、依存、入力の準備)→ **Act**(テスト対象ユニットの実行)→ **Assert**(実際 vs 期待の確認)。
- **依存とフラaky テスト**:IO/外部サービス待ちがテスト速度を殺す;ライブサービス/DB/ネットワークに依存するテストは断続的に失敗 → **flaky test** = コードや環境を変更しないのに結果が一定しない。
- **モック** — 実依存の挙動を模倣する擬似オブジェクト:戻り値を制御し、エラーをシミュレートし、実外部システムには触れない。

## 5. 統合テスト

- 複数コンポーネントが正しく連携するかの検証:REST API エンドポイント、ビジネスロジック、データベース。
- HTTP は Web が情報を送受信するプロトコル;REST API は HTTP メソッド(GET、POST、PUT、DELETE)でデータをやり取り。
- **モッキング**:API は実ビジネスロジックを実行してアプリ自身の DB に書き込むが、**外部サービス(例:決済プロバイダ)はモック** — アプリが制御できないため。

## 6. UI / E2E テスト(Playwright)

- **UI テスト**は UI イベント(キー入力、クリック)を生成し結果を観察;**E2E** は実ブラウザで完全なユーザーフローをテスト。
- **Playwright**(Microsoft、オープンソース):実ブラウザ(Chromium、Firefox、WebKit)を駆動。
  - **シマンティックロケータ** — ユーザーが認知する形で要素を検索(「"Card Number" とラベルされたボックス」、「'Pay' と書かれたボタン」)。
  - **オートウェイト** — `expect` アサーションはタイムアウトまでリトライ。
  - **Happy path**:支払いフォーム入力 → API が検証して Stripe に請求 → 成功メッセージ + Order ID をアサーション(バックエンドが処理済みと証明)。
  - **Unhappy path**:空フォーム → 必須項目エラー;「declined」カード番号 → UI が API エラーをクラッシュせずに適切処理。
  - **モバイルレイアウト**:プログラムでビューポートをリサイズ;フォームのレスポンシブとボタン切れないことを確認。
  - **Headed**(テストを眺めながらデバッグ)vs **Headless**(ウィンドウなし;高速 CI/CD に最適)。
- **Playwright + MCP**(Model Context Protocol):LLM アプリと外部ツール/サービスを接続するオープンプロトコル — AI エージェントが自然言語でブラウザを制御でき、各ステップごとに新しいスクリプトを書く必要がない。
- **演習**:`git clone https://github.com/HKPolyUSE/playwright_testing`;IDE に `@playwright/mcp` MCP サーバを設定;ログインヘルパー例を実行(`doLogin` は `getByRole` ロケータ使用)。

### UI テストのトレードオフ

| 強み | 制限 |
|---|---|
| 常に自動化可能 | ユニットテストより桁違いに遅い |
| E2E カバレッジ(UI → サービス → DB) | 脆い:「Submit」を「Confirm」にリネームするだけでハードコードセレクタが壊れる |
| 高レベル**スモークテスト**に最適(システム起動・デプロイ・接続確認) | E2E 失敗は*何か*が壊れていることは示すが*どこ*かは rarely 示さない |

### 自動テストの全体利点

**速い**(ロードテスト、大量ランダムテスト)、**信頼性**(毎回全く同じ操作、人間エラー排除)、**再現可能**(回帰テスト)。

## 7. テストの形:ピラミッド vs アイスクリームコーン

- **アイスコーン(アンチパターン)**:テストの大部分が手動 + 自動化は UI レイヤに集中;自動化が遅い手動プロセスを模倣しているだけ。
- **テストピラミッド**:
  - **ユニットテスト**(底) — 隔離された関数/メソッド;安価、ミリ秒、即時フィードバック。
  - **統合テスト**(中) — コンポーネント/サービスの連携:API エンドポイント、DB 操作、サービス通信。
  - **UI/E2E テスト**(頂) — UI を通じた完全なユーザージャーニー。

## 8. テスト駆動開発(TDD)

- 通常のフロー:開発 → テスト作成 → テスト実行。
- **TDD のサイクル**:**失敗する**テストを書く → 実行(失敗)→ 通るための最小コードを書く → 実行 → **リファクタ** → 繰り返し(Red–Green–Refactor)。
- **「テスト先行」は設計のこと**:機能コードを書く前に要件や設計を練ることを強制する;API(インターフェース)を設計し、コードが使われる方法を深く考える。よく書かれたユニットテストは**動作する仕様**であり、技術ドキュメントの重要な一部。
- **ちょうど十分なコード**:失敗するテストはギャップを示している;テストを通すだけのコードを書く(実装は最適でない可能性 — 後でリファクタ)。
- **リファクタ**:外部挙動を変えずに設計を改善。
- **TDD の利点**:テストが正しい挙動の「契約」になる;自動テストは全チェックインで実行;チームは意図しない変更を恐れずに機能を提供できる。追加価値:**AI の制約** — テストは AI の変更が全既存テストに合格することを要求し、既に正しい機能が壊されるのを防ぐ。

## 9. ユーザビリティテスト

- 実際のユーザーでインターフェースの使いやすさをテスト。**5 コンポーネント**(Nielsen):**学習性(learnability)、効率性(efficiency)、記憶性(memorability)、エラー(errors:件数/重大度/回復)、満足度(satisfaction)**。
- **ユーザビリティ改善**:代表的ユーザーにリアルなタスクをしてもらう;**観察** — どこで止まり、誤り、混乱するか(印象だけに頼まない);最大の問題を先に直す;再テスト;5 コンポーネント全てで反復。
- **ゲリラテスト** — 低コスト、「野外」スタイルのテスト。
- **実施の流れ**:システムを起動ページに待機;ファシリテータがタスクを指示;思考過程を質問;コメントを記録;開発者/デザイナに観察させる;終了インタビュー(好き/嫌い、提案);**最終レポート**(有効性、効率性、タスク時間、エラー、満足度)を作成。
- **被験者**:特定して募集(日程、場所、ファシリテータ、記録員);**インセンティブ**(無料ランチ、ギフト券)が出席率を向上。
- **ユーザビリティラボ**:シンプルな一室 → 電子観察室。
- **Think-aloud(声出し思考)**:被験者にタスク中に思考を声に出して;何をしているか、何を求めているか、どこが難しかを聞く;温和なプロンプト(「今何を考えていますか?」)。
- **テスト設計**:
  - **独立群デザイン(被験者間)** — 各部分は別のユーザーがテスト;「学習転移効果」を軽減(A を使うと B が楽になり、後期の問題を隠蔽しうる)。
  - **被験者内デザイン** — 各被験者が全モジュールをテスト;**カウンターバランス**(タスク順序のランダム化/バランス)+ セッション間の休憩。
- **データ収集**:
  - *パフォーマンス*:タスク完了時間、正しく完了したタスクの割合(プロンプト有無)、エラー数、エラー回復時間、マニュアル参照回数、ネガティブコメント数。
  - *評価 + 理由*:有用性、期待との適合、使いやすさ/学習しやすさ/セットアップ/アクセシビリティ、ヘルプの品質。
  - *嗜好 + 理由*:本プロトタイプ vs 別プロトタイプ、vs 競合、vs 旧コンセプトモデル。

## 10. キーポイント

- ユーザーがすること(happy path)、境界(edge)、失敗(negative)をテスト — 全て必要。
- 欠陥の大半は仕様/設計由来 → 早期の静的テスト(レビュー)が最も安い欠陥除去。
- 要件は検証可能でなければならない;DRE でプロセスを測定。
- 自動化はピラミッド型:多数の高速ユニットテスト、少ない統合テスト、最少の E2E。
- 外部依存はモックし、テストを速く安定させる;flaky テストを避ける。
- TDD はテストを生きる仕様に — AI 生成変更のガードレールにもなる。
- ユーザビリティは仮説ではなく測定:実ユーザー観察、think-aloud、証拠付きレポート。
