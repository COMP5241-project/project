# AI 支援ソフトウェア開発プラクティス

> コース資料(44スライド)から抽出・整理したノート。コーディングエージェントとの実務ワークフロー:コンテキストエンジニアリング、AGENTS.md ファイル、仕様駆動開発、Agent Skills、AI 生産性の根拠。

---

## 1. Monorepo vs Polyrepo

- **Monorepo** — 関連する複数プロジェクトのコードを単一の Git リポジトリに収容(例:`apps/` フロントエンド+バックエンド、`services/` マイクロサービス、`packages/` 共有 UI/utils、ルートに workspaces)。
- **Polyrepo(マルチレポ)** — 各プロジェクト/サービスを別リポジトリに置く。
- AI 支援コーディングへの開かれた質問:どちらの構成がエージェントの文脈に有利か?

## 2. コンテキストエンジニアリング

### コーディングエージェントのコンテキストウィンドウに入っているもの

会話履歴 · system と agent の設定(ロールプロンプト、安全ルール、プロジェクトプロファイル)· コードとドキュメント(ソース、README、`CLAUDE.md` 等のガイダンスファイル)· 現在のタスク指示と制約 · ツール記述(MCP サーバ・プラグインのスキーマ)· ツール出力(JSON、エラー、ログ)· ストリーミング出力。

### 正しい文脈でモデルを地面に固定する

- **関連する**ファイル、契約、例、最新の API バージョン、社内 SDK を提供 — モデルに推測させない。
- **リポジトリ全体をプロンプトに投入しない**;無関係な文脈を除外し、コストを下げ精度を上げる。
- ライブラリ/ドキュメントを例付きで要約;プロンプトを具体的にする(例:「Streamlit アプリを作成。認証には `st.login()` を使用」)。

> **コンテキストエンジニアリング** = セッション中に LLM が見るものを慎重に選び、品質・信頼性・プロジェクト規約との適合性を高めること。**少なすぎると**効果が下がり、**多すぎると**ノイズが増えコストが上がって、行動が悪化することもある。

## 3. エージェント指示ファイル

特別な Markdown ファイルで、コーディングエージェントが各セッションのたびに自動読み込み、プロジェクトの目的・技術スタック・規約に基づいてプロジェクトスタイルに合ったコードを生成し、誤り(誤ったフレームワーク/ライブラリの使用、リポジトリに既存のコードの書き直し)を減らす。

| ツール | 場所 |
|---|---|
| GitHub Copilot | `.github/copilot-instructions.md` |
| Cursor | `.cursor/rules/*.mdc` または `.cursorrules` |
| Claude Code | `CLAUDE.md` |
| 共通 | リポジトリルートに `AGENTS.md` |

### 良い指示ファイルの内容

- **プロジェクト概要** — 何をし、誰向けで、主要機能は何か。
- **技術スタック** — バックエンド/フロントエンド、フレームワーク、DB、API、テストツール、用途注記。
- **コーディング指針** — スタイル規則、必須テスト、API デザイン、セキュリティ慣行、ファイル/フォルダ慣例。
- **プロジェクト構造** — 主要フォルダとその目的(コード/テスト/ドキュメントの場所)。
- **リソースとツール** — セットアップ/テスト/デプロイスクリプト、カスタムツール、有用ファイル。

### 根拠(AGENTS.md 評価論文)

- **自動生成した AGENTS.md は成功率を約 3% 下げ、推論コストを 20% 以上増やす**(LLM 生成の内容は既存ドキュメントと重複)。
- **人間が書いた AGENTS.md は約 4% の僅かな向上のみ**;エージェントは指示を守るが、不要な要求はむしろタスクを難しくする。
- **含めるべき** — **WHAT**(技術スタック、構造、各部分の役割——モノレポで特に重要)、**WHY**(プロジェクトと主要コンポーネントの目的/意図)、**HOW**(ビルド・テスト・検証の方法;自明でないツール選択、例:`uv` ではなく `pip`、`bun` ではなく `npm`)。
- **含めるべきでない** — 詳細なコードベース概説やディレクトリ一覧(エージェントは構造を自分で発見できる)、時々しか適用されないタスク固有の指示(全セッションの焦点を薄める)、**自動生成の内容**(データ上、害が利を上回る)。

## 4. モデルとワークフローのプラクティス

- **モデルを賢く選ぶ** — LLM にはそれぞれ個性と強みがある;計画/アーキテクチャは推論重視モデル、実装は高速度モデル;1 つのモデルが詰まったら別のサービスに切り替えて盲点を打破。
- **Plan mode** — コードを書く前に詳細な実装計画を作成。
- **小さく、テスト可能な増分で作業** — 巨大な単一プロンプトは不整合・重複・「ごちゃまぜ」を生む。小さなチケットに分解:1 関数を実装 → テストで検証 → 次のステップへ。例:① フロントエンドはモック/偽データで実装、② バックエンド REST API を小さなテストクライアントで検証、③ フロント+バックエンド統合、④ データベース追加、⑤ エンドツーエンドが通ってからリファクタ。
- **頻繁にコミット** — 頻繁な小規模コミットは「セーブポイント」になり、AI コードが軌道を外れた際の素早い巻き戻しに;ブランチ/git worktree を**サンドボックス**として使い、並行する AI セッション同士の衝突を防ぐ。
- **定期リファクタ** — AI 支援コーディングは技術的負債を蓄積;長い関数を分割、大きなモジュールを結合性の高いモジュールに分割、重複を削除(AI は既存コードの再利用より新規生成を好む)、再利用性・テスト性を高める。
- **「チャットはエンジニアリングではない」。** カジュアルなバイブコーディング(会話)は文脈と先見が欠け、「紙の城」を生む — 最初は動くが、コンテキストウィンドウが閉じると保守・デバッグ・スケールが困難に。

## 5. 仕様駆動開発(SDD)

- **仕様優先**:コードを書く前に、AI と仕様を反復して磨く — 要件(エッジケース、ユーザーフロー)、アーキテクチャ(技術スタック)、データモデル(schema)、テスト戦略。
- **SDD の中核**:正式で詳細な仕様は**「実行可能な設計図」であり真実の唯一のソース**;コードは**派生成果物**。開発者は *what* と *why* を定義、AI が *how* を担当。
- ツール:**GitHub Spec Kit**、**AWS Kiro**。

### 主要コンポーネント

- **Constitution**(`constitution.md`) — 交渉不能な原則を定義するガバナンス文書:技術スタック(例:React/Tailwind)、コミット前に必ずテスト実行、TypeScript strict、秘密情報を決してコミットしない、など。
- **機能仕様**(`spec.md`) — 「何を」。
- **技術計画**(`plan.md`) — 「どうやって」。
- **コンテキストファイル**(`AGENTS.md`、`SKILL.md`) — 永続的な指示と「スキル」、AI エージェント向けの「README」。

### ライフサイクル

1. **Specify(仕様化)** — ユーザーストーリー、受入基準、エッジケース、エラー処理要件、成功指標;この段階では技術判断を除外し、純粋にユーザー成果とビジネス価値に集中。
2. **Plan(計画)** — エージェントが spec を消費して技術計画を提案:コードを書く前にアーキテクチャ、データモデル、API 契約を決定;開発者がエンジニアリング基準とプロジェクトの Constitution に適合するかレビュー。
3. **アトミックタスク生成** — 計画を小さなテスト可能なタスクに分解;AI は全体を一度に作らず、1 つのアトミックタスクずつ実行;人間が spec に対して進捗を確認するチェックポイントが可能。
4. **Implement(実装)** — エージェントが rigid な Plan と Spec に従いタスクごとにコードを実装;コードは一貫性を保つ。開発者の役割は構文を書くことから、Phase 1 で定義した受入基準への出力検証へ。

### Spec drift(仕様ドリフト)

- エージェントが spec を確認せずにコードを変更すると、コードとドキュメントが spec から乖離(ドリフト)。
- **バグ = 欠落した要件**:spec をより明確に更新して恒久的に修正。未来のエージェントのための文脈を保持し、人間が手動でコードをパッチする際に起きる回帰を防ぐ。
- 機能追加:コードをパッチするだけでなく、spec に新ロジックを追加 → AI が delta を特定 → plan を更新(新データモデル/サービス)→ 新タスクを生成 → 既存ロジックを壊さずに安全に実装。

## 6. Agent Skills

**アイデア**:AI エージェントは能力が向上しているが、実際の仕事を確実にこなすのに必要な文脈が往々にして欠ける。**Skills** は手続き的知識とチーム固有の文脈を**ポータブルでバージョン管理されたフォルダにパッケージ化し、オンデマンドでロード**する。

- **ドメイン専門知識** — 専門知識(法的レビュー、データパイプライン、プレゼンテーション書式)を再利用可能な指示として捕捉。
- **再現可能なワークフロー** — 多段タスクを一貫した監査可能な手順に変換。
- **クロスプロダクト再利用** — スキルを 1 回作り、スキル対応のエージェントならどこでも使用可能。

### 構造

```
my-skill/
├── SKILL.md      # 必須:メタデータ(name、description)+ 指示
├── scripts/      # 任意:実行可能コード(テスト済み・決定的)
├── references/   # 任意:オンデマンドで読むドキュメント
└── assets/       # 任意:テンプレート、リソース
```

- `SKILL.md` は「エージェントが特定の 1 タスクを完了する方法を教えるマニュアル」— 例:website UI スキルが「青紫グラデーション禁止、emoji アイコン禁止で SVG アイコン使用、フォストグラスのナビバー、hero は半透明オーバーレイ、ブランドアクセント色ボタン」と規定。
- **エージェント別のスキルパス**:`.cursor/skills/`、`.claude/skills/`、`.github/skills/`、`.opencode/skills/`、共通 `.agents/skills/`。
- **SKILL.md が長すぎたら**:各スタイルを独立したリファレンスファイルに分割(`minimalist.md`、`tech-style.md`、`editorial.md`);`SKILL.md` はポインタ付きの要約に — エージェントはまず SKILL.md を読み、関連するリファレンスファイルだけロード。
- **Scripts** はエージェントがテスト済みのスクリプトを呼び出して計算、変換、データ検証、ツール連携を予測可能に行える(例:`python scripts/generate_image.py --style tech`)。

### Progressive disclosure(段階的開示、3 層)

1. **メタデータ**(name + description)— 起動時に常にロード。
2. **Instructions**(SKILL.md 本体)— スキルが選択された際にロード。
3. **任意フォルダ**(scripts/references/assets)— オンデマンドでロード。

エージェントはスキル名/説明の**カタログ**を保持し、「美しいブログサイトを作ってくれ」という要求に `website-ui-design` がマッチすると、完全なガイダンスを引き込む。

### モノリスより組み合わせ可能

- **隔離デバッグ** — フォーカスされたスキルが失敗すれば、壊れたのはどのファイル/パラメータか確実に分かる;規則が衝突するモノリスプロンプトは診断不能。
- **複利的アップグレード** — サブスキルを更新すると、それを使う全親ワークフローが自動でアップグレード;規則の重複腐敗を回避。
- **高コード再利用性** — プラグアンドプレイ;一度スキルとして保存した技術ツールは、どのサブエージェントやプロンプトからも即座にトリガー可能。
- 有名な公開コレクション:Matt Pocock の skills(aihero.dev/skills)、Addy Osmani の agent-skills(Define → Plan → Build → Verify → Review → Ship の各段階、例:`interview-me`、`spec-driven-development`、`planning-and-task-breakdown`、`test-driven-development`、`doubt-driven-development`、`code-review-and-quality`、`git-workflow-and-versioning`、`ci-cd-and-automation`、`shipping-and-launch`)。
- スキルライフサイクルの例(frontend-slides):タスク種類を検出 → コンテンツ質問 → プレビューでスタイル選択 → 単一 HTML ファイルのスライドデッキ生成 → 任意で PPTX 抽出 → 納品(ブラウザでクリックして編集)→ 任意で公開/PDF エクスポート(スクリプト:`extract-pptx.py`、`deploy.sh`、`export-pdf.sh`)。

## 7. 根拠:MERT 研究(2025)

ベテラン開発者によるランダム化対照試験、246 の実世界のコーディングタスク:

- 開発者は AI が **24% 速い**と期待 — 実際は **19% 遅くなった**。
- AI を重度に導入したチームでは、**コードレビュー時間が 91% 増加**。
- **PR サイズが 154% 成長**。
- 「Tab を押して提案を受け入れるたびに生産的だと感じるが、実は完全に理解していないコードを蓄積している」。

## 8. AI 時代のクリティカルスキル

- **システムアーキテクチャとコードがなぜ動くかの理解**は、コードを産出するより重要。
- AI が既存機能の動作を壊す/変更する機能を実装していないことを保証する;生成されたアーキテクチャとコードがスケーラブル・柔軟・保守可能であることを保証する。
- **AI に説明を要求**:「このコードを 1 行ずつ平易な言葉で説明して。」「何という前提を作っている?何が悪い方向にいく可能性がある?」「エッジケースと失敗モードは?」
- **説明できないコードを提出/受入しない。**
- AI 生成コードのレビューでは、欠陥、セキュリティ問題、アーキテクチャ違反を特に狙って探す。
- **定期的に AI なしで練習** — AI が担当するタスク(ボイラープレート、単純なバグ、テスト生成)を学習練習にし、生産の近道にしない。
