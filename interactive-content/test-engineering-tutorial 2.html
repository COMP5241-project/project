Think like a test engineer.

A bartender accepts drink orders. Your job is to turn the rules into checks, try more than the happy path, compare expected and actual behavior, and describe any defect so someone else can reproduce it.

Step 1 · Start with a specification

What should the bar app do?

A test needs a clear oracle: a reliable way to decide whether the result is correct.

Menu

Only known drinks

Beer, coffee, and tea are on the menu. Anything else must be rejected.

Quantity

Whole numbers from 1 to 10

Every order must contain at least one and no more than ten drinks.

Feedback

Explain invalid orders

For invalid input, show a helpful error; do not silently accept the order.

Testable requirement

“A customer can order one to ten whole-number drinks from the menu; all other orders are rejected with an explanation.”

Step 2 · Design more than one kind of test

Cover normal use, boundaries, and invalid input

Strong test sets check both what should work and what the system must refuse.

Happy path

Try a typical valid order, such as two coffees. The app should accept it.

Boundary / edge case

Check the valid limits (1 and 10) and the values just outside them (0 and 11).

Negative test

Try invalid data such as −1, 1.5, an unknown drink, or non-numeric text.

Step 3 · Experiment

Test the bar ordering app

This small system under test has a few planted defects. Set your expectation first, run a test, and compare the result.

Build a test case

Choose an input, classify the test, and state what the specification requires.

Text input lets you try decimals and non-numeric values too.

Test result

Use a preset or edit the input values, then run your test.
